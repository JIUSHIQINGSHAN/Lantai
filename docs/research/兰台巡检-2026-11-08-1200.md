# 兰台巡检 2026-11-08 12:00：插件对话墙与服务端墙等宽，慢提取那轮对话会被连进程杀掉

> 由 Maya（Sesame AI 助手）自动巡检生成，经小号 jiushiqingshand-dev 提交。master 未动。

## 结论

票 73（PR #42，`db4fd54e`）给插件 serve 的读路径接了硬超时墙：注入 5s、对话写入 30s，到点 watchdog
会 kill 整个 serve 子进程。但 serve 子进程自己的对话墙 `settings.SHELL_HOOK_DIALOGUE_TIMEOUT`
默认也是 30s。两墙等宽，到点谁先触发是竞态，实测插件 watchdog 先到：

- 提取超过 30s 的那一轮对话（LLM 慢、排队、重试）静默丢失——服务端本来已经放弃等待、
  让工作线程在后台跑完落库，结果连进程一起被杀；
- 同一进程里其他后台线程一并陪葬；
- 下一次调用要冷启动一个新子进程。

另外，用户在 `.env` 里把 `SHELL_HOOK_DIALOGUE_TIMEOUT` 调大（比如换慢模型调到 60）没有用：
插件写死 30s，照样在 30s 时把子进程杀掉。`SHELL_HOOK_TIMEOUT` 调到 5 以上同理。

## 复现（真插件、真子进程、真 shell_hook 分发与服务端墙）

只把 `_handle_dialogue` 换成「睡 5 秒再写标记文件」的慢函数，把 30s 墙等比缩到 3s。

修复前（master，插件墙 == 服务端墙 == 3s）：

```
server_wall=3.0s plugin_wall=3.0s latency=5.0s
_call_dialogue 返回用时 3.01s；serve 子进程 pid=13437 仍存活=False
等 6.5s 后，对话写入落地条数 = 0 []
下一次调用前 serve pid=13441（换了新进程，冷启动），就绪等待 1.89s
```

修复后（本分支，插件墙自动推导为 3 + 5 = 8s）：

```
server_wall=3.0s plugin_wall=8.0s latency=5.0s
_call_dialogue 返回用时 3.00s；serve 子进程 pid=13448 仍存活=True
等 6.5s 后，对话写入落地条数 = 1 ['13448|s_repro|1|我下周三要去协和医院复查甲状腺结节']
下一次调用前 serve pid=13448（同一进程），就绪等待 0.00s
```

返回时间不变（仍在服务端墙处返回，Hermes 不会多等），只是子进程不再被杀、对话照常落库。

## 改法（只改 `hermes-plugin/lantai-hook/__init__.py`）

- 插件墙 = 服务端墙 + 宽限：注入类 `max(5, SHELL_HOOK_TIMEOUT + 3)`，对话 `SHELL_HOOK_DIALOGUE_TIMEOUT + 5`。
  默认配置下注入仍是 5s（票 73 的承诺不变），对话从 30s 变成 35s。
- 服务端墙的读取口径与 serve 子进程一致：进程环境变量优先（子进程继承），其次仓库根 `.env`
  （settings 的 env_file），都没有就用 settings 默认值；非法或非正值回落默认。插件进程仍然不
  import lantai，只镜像两个默认值，测试锁住镜像与 settings 同步。
- watchdog 只兜「子进程真卡死」；其余票 73 的逻辑（EOF 自愈、`_wait_ready` deadline）未动。
- `docs/lantai-hermes-plugin.md` 同步了墙宽说明。
