## 问题

- 文件：`tests/test_gate_subprocess_encoding.py::test_setx_native_oem_stderr_decodes_cjk_diagnostic`（master 第 179 行起）。
- 测试在 Windows 上取 OEM 代码页（`GetOEMCP()`），然后执行 `"需要管理员权限".encode(f"cp{oem}")` 造一段 setx 的 stderr。
- 中文 Windows 的 OEM 是 cp936，能编码，测试通过。英文 Windows（GitHub windows-latest 就是 cp437）编不出中文，测试在**造样本这一步**就抛 `UnicodeEncodeError`，根本没走到被测函数 `scripts/migrate_home.py::_decode_setx_stderr`。
- 产品代码没错：英文 Windows 上 setx 本来就不会输出中文诊断，`_decode_setx_stderr` 按 OEM 解码是对的。错的是测试假设“OEM 代码页一定能编中文”。

## 为什么一直没发现

- Linux CI 上 `sys.platform != "win32"`，测试走 utf-8 分支，恒绿；OEM 分支只在真 Windows 上执行。
- 用户本机是中文 Windows（cp936），也恒绿。只有在英文 OEM 的 Windows 上才会红，巡检 2026-11-17 在小号 fork 的 windows-latest 上第一次看到。
- 同一写法全仓库只此一处（`git grep GetOEMCP` 只有 `scripts/migrate_home.py:29` 和这条测试）。

## 改法

1. 新增 `_oem_native_sample(encoding)`：能编码中文就用原来的“需要管理员权限”；编不出（cp437/cp850 等）就用该代码页高半区（0x80–0xFF）里的可打印字符拼一段非 ASCII 样本。它用 UTF-8 解会走样，所以仍能证明走的是 OEM 解码。原测试的断言不变，只换样本来源。
2. 新增 `test_setx_stderr_decodes_with_oem_codepage_on_any_host[936|437|850]`：伪造 `ctypes.windll.kernel32.GetOEMCP` 并把模块内的 `sys.platform` 换成 `win32`，让 Linux CI 也能覆盖 Windows 分支。另外断言样本的 OEM 字节和 UTF-8 字节不同，避免样本本身区分不了两种解码。
