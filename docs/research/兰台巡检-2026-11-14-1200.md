## 问题（master `b044b637`）

`tests/test_studio_ui.py::test_studio_layout_in_real_chromium` 用 `--headless --window-size={width},900 --dump-dom` 启动浏览器，再断言页面里的 `innerWidth == width`。

- 你本机找到的是 Playwright 的 `chrome-headless-shell`（老 headless），它认 `--window-size=320`。
- CI 的 ubuntu-latest 上 `shutil.which` 找到的是完整版 Chrome，它的新 headless 把窗口宽度钳到至少 500px。

所以 CI 上 320 档每次都量到 `viewport: 500`，在第一条断言 `row["viewport"] == width` 就失败了（CI 原文：`AssertionError: {'panel': 'panelRecall', 'viewport': 500, 'columns': 1, 'gridWidth': 437, ...}`）。这带来两个后果：

1. master 多了 1 个和代码无关的红。
2. 320px 窄屏布局在 CI 上**从来没被真正检查过**。哪天有人把 CSS 改得在 320 溢出，CI 也只会报同一个 "viewport 500" 的老错，看不出来。

## 改法

只改 `tests/test_studio_ui.py`：

- 被测页面不再直接当顶层页面打开，而是放进一个固定宽度的 iframe 里量。iframe 的视口宽度就是它自己的宽度，媒体查询按它求值，和浏览器窗口的最小宽度无关。宿主页 `/ui/host?w=<宽度>&frame=<页面>` 只有一个 `margin:0` 的 iframe。
- 探针脚本把结果写回宿主页（`window.parent.document`），因为 `--dump-dom` 只导出顶层文档。iframe 的 load 先于宿主页的 load，导出时结果已经在了。
- 原来的断言一条没改：`viewport == width`、列数、`scrollWidth <= width`、卡片宽度大于 0。
- 新增对照测试 `test_studio_layout_probe_catches_overflow_at_320`：给网格强加 `min-width:480px`，320 档必须量出 `scrollWidth > 320`，证明探针真能抓到溢出，不是摆设。
- 生产代码、CSS、HTML 都没动。

## 改完能不能抓到真问题

我把 `lantai/api/ui/styles.css` 和 `index.html` 临时换回 `c1205d55`（也就是 `bc5e3263` 320px 收口之前）的版本，用完整版 Chromium 跑本分支的测试：320 档在 `scrollWidth <= width` 这条断言上失败（`viewport: 320`，`gridWidth: 257`），1440 档照常通过。换回 master 的 CSS 后又全部通过。也就是说，修复后 CI 上真的在按 320px 检查布局，你那次窄屏收口确实有效。
