## 二、已修复发现

### F1（高）常驻 `shell_hook --serve` 循环没有逐帧异常兜底——一帧坏打死整个跨端接力进程

- **证据**：`main()` 的 serve 分支只对渲染（`render_host_response`）有守卫，`_handle_one` 无包裹。
  `_handle_one` 内 `assert_hook_api_key_configured()` 在未配 `API_KEY` 时抛 `HookAuthError`；
  协议层/适配层任何未预期异常同理。子进程退出 → Hermes 插件侧读到 EOF（`_call_dialogue` 等
  只记 warning 并复位 `_proc`）→ 下一次调用 `_ensure_proc` 冷启动 + `_wait_ready` 约 15s，
  **该帧与之后每轮注入全部丢失**。协议文档 §3 明写「hook 绝不抛异常、不拖垮宿主」，未兑现。
- **修复**：serve 循环逐帧 `try/except Exception`，降级为空帧 `{}` 并留 stderr 痕，循环继续；
  畸形帧既有 `{}` 语义不变。改后 `tests/test_shell_hook.py::test_serve_mode_survives_handler_exception`
  （红→绿：注入一次异常后第二帧仍应答，共 2 帧、进程不抛）。
- 位置：`scripts/shell_hook.py` `main()`。

### F2（高）缺表自愈只覆盖 stdio 对话通道，REST 两条写通道撞滞后库直接 500

- **证据**：旧实现在 `scripts/shell_hook.py::_handle_dialogue` 内联「捕获 `no such table` → `init_db()` → 重试」。
  `lantai/api/routes_dialogue.py` 的 `POST /dialogue`（同步 `ingest_dialogue`）与
  `POST /dialogue/async`（`submit_async_dialogue` 先 `start_ingest_event`）都没有这层：
  库 schema 滞后（真实库 v44 vs 代码 v47 的实测形态）时，HTTP 侧在「提交」阶段就 500，
  宿主连 `task_id` 都拿不到；而 stdio 侧已能自愈——同一病灶两套行为。
- **修复**：新增 `lantai/storage/schema_guard.py` 作为单一真源（`is_missing_table_error`
  + `heal_missing_schema`）。自愈下沉到 `ingest_dialogue` 入口（覆盖 REST `/dialogue` 全管线）
  与 `async_ingest_service._start_ingest_event_selfheal`（覆盖 `/dialogue/async` 提交阶段）；
  `shell_hook._handle_dialogue` 退化为「补建后仍失败 → `ok=false` 如实上报」。约束：
  - 只认 `no such table`；锁冲突/磁盘满等不重试（重试治不了那些病）；
  - 同一 engine 至多付一次 `init_db` 代价（并发自愈不叠加；修复失败撤销登记可再试）；
  - 修复失败不吞：调用方按既有口径上报（钩子 `ok=false`、HTTP 5xx）。
- 测试：`tests/test_dialogue_schema_selfheal.py` 新增 3 项——HTTP 侧（不经钩子）直调
  `ingest_dialogue` 自愈落候选（fastpath 文本，不 mock 被测逻辑）、同 engine 只跑一次 `init_db`、
  非缺表 `OperationalError` 不触发自愈且只尝试一次。原 3 项（钩子自愈/重试失败上报/非 schema 零侵入）保持绿。

### F3（中）`/dialogue/async` 任务注册表无界增长 + worker 撞被清扫行静默死掉

- **证据**：`_TASKS` 每轮提交写一条、永不淘汰（`result` 含候选正文）；服务常驻数天即数万条 dict。
  `_execute_dialogue_task` 用 `_TASKS[task_id]` 直接取行，一旦注册表被清理（测试 `clear_tasks`、
  将来任何清扫）后台线程抛 `KeyError` 静默死掉、幂等 claim 不结算——同文重试永远停在 pending。
- **修复**：终态任务 1h TTL 清扫 + 1000 条硬顶（超顶从最旧终态淘汰，`queued`/`processing`
  绝不淘汰）；worker 改 `get` 取行，行缺失时释放 claim（`settle(ok=False)`）并留痕。
- 测试：`tests/test_async_task_registry.py` 4 项（TTL 只清终态、硬顶淘汰最旧终态、缺行释放 claim、
  正常路径零漂移）。提交路径的清扫点由既有 `test_async_ingest.py` 覆盖。

### F4（中）`scripts/lantai_mcp_bridge.py` 帧上限形同虚设（内存安全 + 协议应答）

- **证据**：`main()` 用 `for line in sys.stdin` 先整行读入内存，再判 `len(line) > 1_000_000`——上限
  阻止不了大帧占内存，一个超大坏帧可撑爆桥进程，宿主只见 EOF、记忆通道失联。打包版
  `lantai/cli/mcp_bridge.py` 已按上限 `readline` 并回 `-32600`，副本未对齐。
  另：`except ValueError: os.environ.setdefault("PYTHONIOENCODING", ...)` 是死代码
  （运行期改环境变量对已建流无效，shell_hook 已踩过同一坑）。
- **修复**：改用 `sys.stdin.buffer.readline(_MAX_FRAME+1)`；超长帧排空到行尾后回
  `{"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Oversize frame"}}` 并继续；
  坏 UTF-8/坏 JSON 帧跳过不打断循环；编码回退改为如实 `warnings.warn`。
- 测试：`tests/test_mcp_bridge_frame_bounds.py` 3 项（真实子进程 stdio：超长帧→-32600 且下一帧应答、
  坏 UTF-8 跳过、坏 JSON 跳过）。

### F5（低，但会随机红全量）测试夹具控制令牌首字符 `-` 导致 DSH 契约用例随机失败

- **证据**：全量跑测出现一次 `test_dsh_dialogue_extraction_contract.py::...[api-key]` 红，
  失败栈是 fixture 子进程报 `argument --control-token: expected one argument`。
  根因：`IsolatedCoreMemoryServer` 用 `["--control-token", token]` 逐位传参，而
  `token = secrets.token_urlsafe(24)`（urlsafe base64 字母表含 `-`），首字符约 1/64
  概率是 `-`，argparse 把它当选项 → 整个 DSH 契约用例集在启动 fixture 阶段随机红，
  与产品代码无关，却会让「全绿」结论不可复现。
- **修复**：改为 `--control-token=<token>` 单参数形态（与首字符无关），并在
  `tests/test_dsh_core_memory_contract.py` 增加回归锁（强制令牌以 `-` 开头，fixture
  必须仍能启动）。

## 三、残余风险与交叉互审议题（本轮不改）

1. **双份 MCP 桥分叉（建议全局互审裁决）**：`lantai/cli/mcp_bridge.py`（打包版：`http.client`、
   帧/响应上限、主机与 id 校验、无重定向）与 `scripts/lantai_mcp_bridge.py`（DSH 部署用的独立副本：
   `urllib`、无响应上限、90s 固定超时、校验较少）是两套实现。DSH 接入文档要求部署 scripts 副本，
   于是更强的防护只装在打包侧。收敛需要产品决策（单一实现 + 独立部署形态，或生成式同步）。
2. **stdio 单管道的队头阻塞**：serve 是「一行请求一行响应」的单线程循环，对话写通道单帧最多
   阻塞 30s（`SHELL_HOOK_DIALOGUE_TIMEOUT`，含 LLM 提取），期间下一轮 `query` 帧只能排队；
   会话结束时插件逐条 flush（N 条消息 = N 次串行提取）。超时墙保证不永久卡死，但「零阻塞」
   只是有界阻塞。建议后续：对话通道在 serve 侧改为「立即回执 + 后台单 worker」（需重议
   `ok=false` 可观测性），或插件侧把 flush 批量化为一次请求。
3. **插件 flush 的丢失窗口**：`_flush_session` 先 `pop` 缓冲再逐条 `_call_dialogue`；子进程中途
   死亡时剩余消息只进日志、无重投。重投有重复入库风险（同步对话通道无幂等键），需先设计去重再补。
4. **`turn` 契约不一致**：协议为 1-based（stdio 层把 0/负数/布尔静默置 None），但
   `DialogueIngestReq.turn` 与 MCP 桥 schema 允许 0 → HTTP 会把 `origin_turn=0` 写进 provenance。
   建议在路由层对齐 stdio 的「丢弃非法 turn」口径（改动小，但要同步桥 schema）。
5. **NDJSON 无请求关联**：`_request_line` 按「位置」匹配响应，依赖 serve 侧严格一请求一行。
   若将来对话通道异步化或加批量回执，必须先引入 request id，否则迟到帧会错位。
