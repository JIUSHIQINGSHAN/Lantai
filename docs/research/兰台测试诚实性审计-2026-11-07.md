### 1a. 运行环境坑（基线首跑即撞，如实入账）

直接按任务给的形态 `<主仓 venv python> -m pytest tests` 跑，**conftest 加载即失败**：

```
ImportError while loading conftest 'D:\Projects\.wt-v068-tests\tests\conftest.py'.
    from tests.support import harness_state
E   ModuleNotFoundError: No module named 'tests.support'
```

而外层管道退出码仍是 **0**（`tee` 掩蔽 pytest 退出码——流 A §15/§23 已两次取证的同族陷阱，
本次第三次实锤）。机理：本会话环境变量 `PYTHONPATH` 被 ambient 污染（指向 hermes-agent 安装树），
`tests` 顶层名解析到了错误位置；且 pytest 9.1.1 下 `pyproject.toml` 的 `pythonpath = ["."]`
未能救回 conftest 加载期。**修复**：显式 `PYTHONPATH=<worktree 根>` 后收集正常。
这是「运行级假绿/假红」形态的环境面证据：同一条命令在干净 shell 与污染 shell 下结果
完全不同，且失败被管道吞成 exit 0——CI/门禁若复用这种管道形态，会把「零用例执行」
记成全绿。流 A §23（运行级假绿新形态）与本节互为印证。

## 2. 方法

新写 AST 扫描器 `tools/audit_dishonesty.py`（工件在 `.scratch/v0.68-test-honesty/`，
与流 A 的 `audit_honesty.py` 并列）：对 `tests/` 全部 `*.py` 做 AST 遍历，按五类产出
`file:line + 证据 + 机理` 嫌疑清单（`dishonesty.json`），再逐条人工复核代码上下文。

**扫描器自身经历两轮误报修正**（如实记录，工具的结论只在修正后可信）：

1. `test_db`/`test_client`/`test_client` 等 **fixture 名以 `test_` 开头**被误判为测试
   （无断言 = fixture 本来无断言）——修正：`@pytest.fixture` 装饰器（带参/不带参两种
   AST 形态）排除；
2. `m.assert_called_once_with(...)` 等 **mock 断言**未被计入有效断言——修正：
   `assert_*` 属性调用计入；
3. `self._assert_filename_only(...)` 等 **方法级 assert helper** 漏查——修正：
   登记类方法后复核。

修正后总量 297 条嫌疑：A-无断言 9 / A-弱断言 4 / B-mock过重 206 / C-静默跳过 4 /
D-时钟负载 26 / E-共享状态 48。**每一条都人工读了代码上下文**，判定如下。

## 3. 五类判定（逐类给证据与结论）

### A. 无断言 / 弱断言 —— **无高危**

9 条「无断言」全部是**「不抛即过」的负向契约测试**，docstring/注释明说语义，
非恒绿：

| 位置 | 形态 |
|---|---|
| `tests/test_llm_degrade_and_git_sha.py:153` | `record_llm_outcome(...)` 遥测自身失败必须静默（注释「不抛即过」） |
| `tests/test_migration_chain_isolation.py:360` | `init_db` 一块失败仍正常返回（「拒绝启动会让服务起不来」） |
| `tests/test_offload_none_principal.py:135` | `ensure_can_delete(None, ...)` 钉住现状（行为改变时红） |
| `tests/test_ownership_migration.py:266` | 表不存在时迁移只记日志不抛 |
| `tests/test_scheduler.py:287` | `stop_scheduler` 幂等不抛 |
| `tests/test_settings.py:118` | `validate_config()` 不 crash（warn 形态另有一条带真断言） |
| `tests/test_ssrf.py:33` | `validate_fetch_url("https://8.8.8.8/...")` 不抛即过（拒绝型校验函数的允许路径） |
| `tests/test_auth.py:176,183` | `assert_secure_binding()` 不抛即过（被测函数名即断言语义） |

对「拒绝型/幂等型」被测函数，「不抛即过」**就是**有效断言（函数错误地拒绝/抛错时红）。
低危建议（不阻塞）：给这几条补一行注释标注「不抛即断言」的约定即可。

4 条「弱断言」（唯一 `is not None`）经复核**全部误报**：`assert X is not None and X[...]`
复合断言（`test_checkpoint_write_owner.py:134`），或「存在性」本身就是用例语义
（`test_core_time.py:74` 写库守门、`test_document_cascade_ownership.py:211` 记忆未被删、
`test_consolidation_index_sync.py:124` FTS 行提交后仍可见）。

### B. mock 过重 —— **无高危**

206 条嫌疑按 patch 目标/形态分组复核，全部落进三类**有正当语义**的形态：

- **外部替身（AGENTS.md 允许）**：`ChromaVectorStore`×6、`Mock(search=...)` 作向量库×100
  （抽样 `test_distill.py:237`、`test_fts_integration.py:151`——BM25/FTS 通道与闸门管线
  全部真实执行，Mock 只替向量库）、`lantai.llm/retrieval.intent.chat_json`、
  `lantai.core.time.utcnow`×3（时钟冻结，合理）；
- **故障注入**：`test_fts_integration.py:580/616` patch `search_fts_bm25`/
  `search_fts` 为 `side_effect=sqlite3.OperationalError`——注入通道故障测**降级留痕**
  （「BM25 通道失败必须留痕，不得静默 pass」），是合法测试技术而非假绿；
- **transport 接线**：`lantai.cli.mcp` handler 测试 patch service 层
  （`test_mcp.py:247/411/456` 等）并 `assert_called_once_with(principal=None)`——测的是
  MCP 工具的**参数接线**；service 逻辑本体由流 A 台账中的直调冒烟覆盖
  （`candidate_review`/`rollback`/`add_raw_memory` 均已登记 real-smoke）。

patch 频次最高的 `lantai.gate.decision.check_contradiction`×15 是 **LLM 矛盾判定替身**
（外部网络面），被测的是 `decide()` 的规则分派逻辑，真实执行。

结论与流 A「mocked-only/hollow-smoke 双清零」交叉印证：**本仓当前不存在
「patch 掉被测核心逻辑自身」的恒绿测试**。

### C. 静默跳过 —— 4 条，**1 条防御性死分支 + 3 条条件跳过，均低危**

| 位置 | 形态 | 判定 |
|---|---|---|
| `tests/test_longmemeval_core.py:141` | `pytest.skip("预注册未生成")` | **死分支**：`docs/benchmarks/longmemeval-2026-10/preregistration.json` 已入仓（v0.25 嘉量），此 skip 永不触发。防御性代码，可留 |
| `tests/test_mcp_principal_wiring.py:637,677` | `pytest.skip("AUTODREAM_ENABLED=false")` | 环境条件跳过，条件明确写死在测试内 |

此模式需要换成 fail（宁红不 skip）。

### D. 时钟/负载敏感 —— **3 处高危假绿窗口（本轮真问题，已补强）**

26 条嫌疑复核后，多数为确定性或低危：

- `tests/test_coalesce_session_key.py` 的 `time.sleep(0.06)`×6：`CoalesceBuffer.check_idle()`
  是**惰性时间判断**（`now - ts >= idle_timeout`，`lantai/ingestion/coalesce.py:132`，
  不起线程）——sleep 只是把墙钟推过窗口，判定确定性成立，**非竞态**；
- `tests/test_async_ingest.py` 的 `sleep(0.1)`×3：带 2s 上限的**轮询等待**（20×0.1s），
  被测 worker 瞬回，模式可接受；
- `tests/test_persona_injection_fence.py` 的 `sleep(1)`×3：慢替身只为触发超时墙，
  断言本身不含墙钟（但见下——内容断言导致「降级与否都绿」，仍属假绿）；
- `tests/test_hook_timeout_budget.py:107` `sleep(0.5)`：`_run_with_timeout` 超时路径
  直调测试，返回值断言锁死降级工厂语义，墙失效时 `== {"context": "never"}` 会红，非假绿。

**真问题（高危）——「超时墙」测试的降级路径可能从未被走到，绿是掩护出来的**：

1. `tests/test_hook_timeout_budget.py:93`（原状）：`embed_delay=1.0`、`timeout=0.2`、
   `assert elapsed < 1.5`。**若超时墙完全失效**（预算丢失/根本不等），慢 embed 等满
   ≈1.0s 返回，`1.0 < 1.5` **依然绿**——「超时降级」测成「降级与否都绿」。
2. `tests/test_shell_hook.py:78`（原状）：两处慢替身各 1s、`timeout=0.2`、
   `assert elapsed < 3.0`。墙失效时串行等满 ≈1~2s，`< 3.0` 依然绿——同款。
3. `tests/test_persona_injection_fence.py:199-257`（原状）：两个「超时降级」用例
   （墙 0.05s）只断言**返回内容**；`test_with_persona_...` **连链上慢点都没有**
   （只 patch 了无调用点的 `mod.embed`），「超时」全靠 jieba 冷启动的自然耗时撞墙——
   **机器冷热敏感**：jieba 冷时降级发生、热时墙永不触发走零命中正常路径，而内容断言
   两条路径都绿。

这三处正是任务点名的历史 flaky 同族（`.scratch/watch/build-context-2s-timeout-flaky.md`
所述 build-context 2s 超时问题；**该文件在本 worktree 与 git 历史中均不存在**，从主仓
工作区清理情况看已不可考——此处如实记录）。补强见 §4。

另：`test_hook_timeout_budget.py:171-180` 与 `test_shell_hook.py:75` 的墙钟断言已带
「契约 1（确定性，与机器快慢无关）」注释与正确余量，判中低危可接受。

### E. 共享状态污染 —— **无高危**

48 条全部是**模块级容器**，逐一核对后分两类：

- **只读测试数据**（26 个文件）：`BLOCKS`/`PAPERS`/`FROZEN_DEFAULTS`/`BENCHMARK_CASES`
  等，grep 核对无 `append`/`__setitem__` mutate，模块级常量不构成跨测试污染；
- **有意设计的护栏台账**（`tests/conftest.py:176` `_PREV_TEST`、
  `tests/support/harness_state.py:40` `HARNESS_ENV_POLICY`、
  `tests/support/network_egress_tripwire.py` / `real_home_tripwire.py` `_current`）：
  注释明确记载其防污染用途（每个测试 setup 校验、会话结束复原），是治理设施而非病灶。

基线运行的护栏输出也印证台账在工作：1 例造脏被当场回滚并点名。

## 4. 补强（3 处，每处一个提交，全部真跑验证 + 变异验证）

补强原则：**只收紧、不放宽、不加 skip**。深挖后（见 §4a）三处统一为同一配方：
**强制走检索路径（relevance 放行 + intent=fact_lookup）→ 在真实慢点
（`lantai.retrieval.hybrid.embed`）放慢替身 → 三向断言**：
① 降级签名——`event_id` 不在返回里（`_query_fallback` 只返回画像段不带 event_id；
正常路径**含零命中分支**必带 event_id，v0.68 票 01）；② 墙真的等了（`elapsed >= timeout`）；
③ 没等满慢替身（`elapsed < 替身时长`）。daemon 线程超时即弃
（`scripts/shell_hook.py:623` `self.daemon = True`），替身加长不拖测试收尾。

1. **`test_hook_timeout_budget.py::test_dispatch_query_timeout_returns_persona`**
   （提交 2）。原病三层：`embed_delay` 是死参数（shell_hook 内 import 的 embed 无
   调用点，慢点根本不在链上）；conftest 假 chat_json 让 hybrid_search 在 intent 短路
   **零命中**（不调 embed、几十毫秒走完正常路径）——「超时」只剩 jieba 冷启动的自然
   耗时能撞墙（**机器冷热敏感：热身后墙永不触发**）；上限 `< 1.5s` 吃掉「墙失效等满
   1s 替身」的窗口。三者叠加 = 降级与否都绿。
2. **`test_shell_hook.py::test_main_timeout_returns_empty_json`**（提交 3）。同款
   intent 短路问题；好在 `json.loads(out) == {}` 本身就是降级签名（无画像时正常路径
   零命中会带 event_id），补 intent + 慢点 + elapsed 区间后三向锁定。
3. **`test_persona_injection_fence.py` 两个超时降级用例**（提交 4）。最深一层：
   `test_with_persona_timeout_returns_fenced_context` **连真实慢点都没有**（只 patch 了
   无调用点的 `mod.embed`），「超时」全靠 jieba 冷启动撞墙；`test_no_persona_...` 的
   慢点在链上但同样受 intent 短路影响。补齐慢点 + intent + 双确认断言
   （event_id 缺失 + elapsed < 1.0s）。

### 4a. 深挖过程（变异验证暴露的连环假绿，如实记录）

补强不是一次写对的。第一版只加了 elapsed 区间断言，**变异验证**（把墙临时改成
失效值，期望红）暴露了连环问题：

- 变异 A（墙 0.2s→10s，失效成「不掐」）在旧版补强下**依然绿**——追出 `embed_delay`
  死参数与 intent 短路（`HYBRID_EMBED_ATTR` 插桩实证：用例 patch 后 `hybrid.embed`
  仍是 conftest 的 `_fake_embed`，0.022s 走完零命中正常路径）；
- `test_with_persona` 补上 event_id 断言后**正版直接红**——它原本就没有链上慢点，
  旧绿全靠 jieba 冷启动；单跑绿（jieba 冷）合跑红（jieba 热）正是同一机理的
  顺序敏感表现；
- 最终版补齐 intent + 链上慢点后，验证矩阵全绿且两个变异方向如期红：

```
=1 正版三文件:            41 passed in 9.40s        （补强前同集 41 passed in 11.53s）
=2 原互踩 pair:            2 passed in 5.00s         （main → with_persona 顺序）
=3 变异A 墙=10s 期望红:    2 failed（event_id 断言红）✓
=4 变异B 墙=0.001s 期望红: 1 failed（elapsed 下限红）✓
```

变异副本即造即删，不入库。
