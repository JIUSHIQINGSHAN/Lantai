## CI 现状：本地 0 失败，GitHub 3 失败

- GitHub：`2f952cf4` 的 Tests 工作流（push）是 3 failed, 2848 passed, 6 skipped。上一次 PR #21 的运行（`0f3f4859`）也失败了。
- 本地（Python 3.13，uv 环境）：`2f952cf4` 全量 2852 passed, 5 skipped, 0 failed。

门禁文档说「主干红在本 HEAD 不成立」，在本地成立，在 GitHub 上不成立。三个失败如下。

### 1–2. `test_legacy_schema_parity` 的两条：CI 是浅克隆，没有历史 tag

- 失败用例：`test_legacy_snapshot_matches_real_old_version`、`test_v0650_is_ancestor_and_still_lacks_shared_scope`（票 06 新加）。
- CI 日志：`git show v0.25.0:...` 报 `fatal: Needed a single revision`；`git merge-base --is-ancestor v0.65.0 HEAD` 报 `Not a valid object name v0.65.0`。
- 原因：`actions/checkout` 默认 `fetch-depth: 1`、不拉 tag。本地是完整克隆，所以本地门禁看不到。
- 修法：`tests.yml` 和 `ci.yml` 的 tests 作业都加 `fetch-depth: 0`（拉全部历史和 tag）。没有把用例改成浅克隆时 skip——仓库的门禁规则本来就不认 skip 当 pass。

### 3. `test_importing_mcp_does_not_mutate_sys_path`：setuptools 自己改的 sys.path

- CI 断言：`import lantai.cli.mcp 改写了 sys.path：['/opt/hostedtoolcache/Python/3.11.17/x64/lib/python3.11/site-packages/setuptools/_vendor']`。
- 原因：兰台很多模块在顶层 `import jieba`；`jieba._compat` 会 `try: import pkg_resources`。setuptools 81 以前的 `pkg_resources` 在 import 时把 `setuptools/_vendor` 追加进 `sys.path`。CI 用的 toolcache Python 3.11 自带 setuptools；`uv.lock` 里没有 setuptools，所以本地 uv 环境里 `pkg_resources` 不存在、用例通过。
- 复现：在 Python 3.11 venv 里装 `setuptools<81`（实测 80.10.2），用例稳定失败，报的就是 `setuptools/_vendor`；装 setuptools 84 时不复现（`pkg_resources` 已被移除）。
- 修法：探针在记录 `before` 之前，如果 `pkg_resources` 可导入就先导入它。只排除 setuptools 这一个来源；兰台模块和 jieba 自己对 sys.path 的改动仍会报出来。
- 验证：同一个 3.11 + setuptools 80.10.2 环境，改前 `test_mcp_import_side_effects.py` 1 failed / 5 passed，改后 6 passed。变异对照：在 `lantai/cli/mcp.py` 顶部临时加一句 `sys.path.insert(0, "/tmp/mutation-probe")`，改后的用例照样报红（`['/tmp/mutation-probe']`），还原后通过。

顺带：在 setuptools<81 的环境里，`import jieba` 会多花 90–225 毫秒载入 `pkg_resources`，还打一条 `pkg_resources is deprecated` 的 UserWarning（实测三次 125/225/91 ms）。这是 2 秒注入预算里的实打开销，但你的 uv 环境没有 setuptools，所以只写成建议，没动产品代码。

## 没进主干的四处修复（从 PR #20 搬过来）

PR #20 和 v0.66 在 9 个文件上冲突：v0.66 自己实现了测试隔离、豁免归档和注入保活，这些本 PR 不再搬。下面四处在 `2f952cf4` 上仍然存在，搬过来的用例在主干上跑，9 条里 6 条失败（5 条是行为复现，1 条是无预算仍重试 3 次的结构断言），终端编辑的 2 条里 1 条失败。

1. **精排在 `.env.example` 推荐配置下被静默关掉**（`lantai/retrieval/reranker.py`）：X-09 把「同一服务商」写死成 `api.openai.com`。按推荐配置（`OPENAI_BASE_URL` 和 `RERANKER_BASE_URL` 都是硅基流、不单独配 `RERANKER_API_KEY`），精排每次都跳过。改成比较 `OPENAI_BASE_URL` 与 `RERANKER_BASE_URL` 的实际 host，防泄漏的作用保留：OpenAI 密钥仍不会发给硅基流。
2. **预算模式下 embed 和 rerank 还在重试**（`lantai/llm/client.py`、`lantai/retrieval/reranker.py`）：`embed` 整体被 `@retry(stop_after_attempt(3))` 包住，SDK 自带重试也没关；11-01 实测一次调用 3 个请求、耗时 3.54 秒，超过 2 秒预算。rerank 给了 timeout 还是「请求 + sleep + 再请求」。修法：tenacity 只包无预算路径（`_embed_with_retry`），预算模式 `max_retries=0`；rerank 给了 timeout 只试一次。无预算调用行为不变。
3. **无预算时也传 `timeout=None`，评测静默变成纯关键词**（`lantai/retrieval/hybrid.py`、`lantai/eval/deterministic_embed.py`）：单参的 `embed_for_eval` 被 patch 到 `hybrid.embed` 后抛 `TypeError`，被 `except` 吞掉，只留一条「Vector search failed, falling back to keyword」。只在给了预算时传 timeout，`embed_for_eval` 也接受 timeout。
4. **终端编辑接口没有注入闸**（`lantai/api/routes_terminal.py`）：merge 和 correct 都有 `assert_no_prompt_injection`，`PUT /terminal/memory/{id}` 没有。主干上用它写入「忽略之前的所有指令…」仍返回 200 并重嵌入，下一轮就会被 Hermes 注入。现在返回 422、不入库。

搬过来时发现一处要跟着改的用例：v0.66 的测试装配把 `OPENAI_BASE_URL` 强制指向黑洞地址，`test_reranker_key_leak_guard.py::test_openai_host_allows_fallback`（前提是「两边都是 api.openai.com」）原来靠出厂默认值成立。现在用例显式设了 `OPENAI_BASE_URL=https://api.openai.com/v1`，断言不变。

## 建议（没改代码）

### P0：注入保活加 use_count，考功会把天天在用的记忆降到 0.1

- v0.66（`93e73ac7`）让 `backfill_used_ids` 在每次宿主回执时给被用的记忆 `use_count += 1`。Hermes 插件每轮注入都发回执（`hermes-plugin/lantai-hook/__init__.py` 的 `_backfill_receipt`），但插件和 shell hook 都不发「有用」反馈；全仓库只有 `reflector.record_feedback` 会加 `helpful_count`。
- 考功（`lantai/cognition/kaogong.py`）的规则是 `use_count >= 3` 且采纳率 <= 0.2 就「下考」，重要度直接写成 0.1。
- 本地复现（真实 SQLite、真实 `log_retrieval` / `backfill_used_ids` / `KaogongEngine.run_cycle` / `apply_forgetting`）：一条重要度 0.95 的「我对花生过敏」，经过 3 轮注入回执后 use_count=3、helpful=0；用具名用户身份跑一次考功（对应 `POST /evolution/kaogong` 或 `POST /kaogong/eval`），重要度 0.95 → 0.1，理由「考功下考：高频低效（0/3 = 0.0%）」。之后 160 天没用就被归档；不跑考功时，同一条记忆 160 天后仍是 active（高重要度豁免）。
- 现在不会自动发生：考功没有定时任务，MCP 入口不带身份会空转。但只要你在终端或 API 上跑一次考功，最常用的记忆会整批被降权。三省（`use_count >= 5` 且 helpful=0）也会把它们全标成异常。
- 可选改法：① 回执只刷 `last_used_at`，另记一个「注入次数」字段，考功和三省继续只看显式反馈；② 考功下考要求至少收到过一次显式反馈；③ 让 Hermes 插件在回执里带上「这条被回答引用了」的信号。这是产品取舍，我没替你选。大约 1 天。

### P1：本地门禁补上「CI 环境」这一维

这次三个失败都是本地和 CI 的环境差：完整克隆 vs 浅克隆、uv 环境 vs 自带 setuptools 的 3.11。门禁做了很多自证，但没有一项在「和 CI 一样的环境」里跑。建议 `release_check.py` 加一项：读最新一次 GitHub Tests 运行的结论（`gh run list`），或在 `git clone --depth 1` 的副本里用 3.11 跑一遍全量。大约半天。

### P2

- jieba 在 setuptools<81 的环境里会拖进 `pkg_resources`（90–225 ms + 一条弃用告警）。如果你或别人用 pip + 系统 Python 3.11 装兰台，冷启动会吃掉这部分预算。可以加一个 jieba 导入封装，导入时暂时屏蔽 `pkg_resources`（jieba 有现成的失败回退路径）。
- CI 上 6 个 skipped，本地 5 个，门禁文档记的是 0 skipped。建议在 CI 里加 `-rs` 把跳过原因打出来，和门禁的「skip 不当 pass」规则对一下。
