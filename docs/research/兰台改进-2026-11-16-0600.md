# 兰台改进：CLI 模式的 shell hook 在真 Hermes 下一次都没检索过

> 小号 jiushiqingshand-dev 提交。这是用户要求的专项查证：查 CLI 模式的 `scripts/shell_hook.py` 有没有插件那边「每轮 `on_session_end` 被当成整场结束」的问题。分支 `improve/20261116-0600-hermes-shell-hook-payload`，基于 master `cf4804f0`。

## 一句话结论

**插件那个问题 CLI 模式没有，但 CLI 模式有一个更早一步的问题：它在真 Hermes 下每轮都按空查询处理，记忆一次都没注入过。** Hermes 把本轮用户原话放在 stdin 的 `extra.user_message` 里，`parse_host_request` 只认顶层 `query`/`message`/`prompt`。这个 PR 让它在顶层三字段都缺、且事件是 `pre_llm_call` 时改读 `extra.user_message`，只动归一化层一个函数，没碰 `hermes-plugin/lantai-hook`。

## 1. 原来要查的问题：CLI 模式没有

- CLI 模式下 Hermes 只调 `pre_llm_call` 这一个 shell hook（`docs/hermes-install-handoff.md` Step 3 也只配了这一个），`shell_hook.py` 对这类帧只做检索注入。
- 它不写对话、不写底本、不读「上次在做」。真 Hermes 跑完两场会话后，`session_checkpoint` 是 0 行、`rawdocument` 是 0 行。所以「轮次号永远是 1、在做被最后一句盖掉」在 CLI 模式下不会发生——因为 CLI 模式根本没有这条写通道。
- 反过来说，CLI 模式下新会话也拿不到「上次在做」。要底本，得用插件。

## 2. 真正的问题：Hermes 的 shell hook 线格式和兰台对不上

Hermes v0.23.1 `agent/shell_hooks.py::_serialize_payload` 给 shell hook 的 stdin（官方文档 `user-guide/features/hooks.md`「JSON wire protocol」一节同样写明）：

```
{hook_event_name, tool_name, tool_input, session_id, cwd, profile, extra}
```

事件参数全在 `extra` 里，`pre_llm_call` 的原话是 `extra.user_message`。顶层没有 `query`/`message`/`prompt`。`lantai/integrations/host_protocol.py` 的回落分支只认这三个顶层字段，于是 query 永远是空串，`build_context` 直接返回 `{}`。

## 3. 复现：真 Hermes v0.23.1 + 假模型，CLI 模式

环境：云端一套独立的 Hermes 环境，`hermes chat -Q -q` 逐轮驱动（会话内用 `-r <session_id>` 续接），profile 里只配 `hooks: pre_llm_call` 指向 `scripts/shell_hook.py`，**不启用 lantai-hook 插件**。每次跑前清空 LANTAI_HOME、`init_db`、用 `create_skill` 零 LLM 写入一条技能记忆「兰台发版流程」。外面包一层脚本，把 Hermes 实际喂给 hook 的 stdin 原样记下来。

两场会话：第一场三轮（「决定了：v0.68.1 先把票83红测加 xfail…」「下一步我去补 CHANGELOG…」「好的谢谢，我去吃饭了」），第二场一轮（「兰台发版流程是什么？我上次做到哪了」）。

| | master `cf4804f0`（hook 代码与 `fc4fb2c8` 相同） | 本分支 |
|---|---|---|
| Hermes 喂给 hook 的 stdin | 4 帧都是 `hook_event_name=pre_llm_call`，顶层无 query/message/prompt，原话在 `extra.user_message` | 同左 |
| hook 返回 | 4 个 `{}` | 3 帧返回 `context`（带 `event_id`），「好的谢谢，我去吃饭了」被闸门跳过返回 `{}` |
| 模型收到的用户消息 | 只有原话，没有任何记忆 | 原话后面接上「本次依据 / 相关记忆」，命中「兰台发版流程」 |
| retrieval_event | 0 行 | 3 行，`session_id` 是 Hermes 的 `local-…` 会话号 |
| session_checkpoint / rawdocument | 0 / 0 | 0 / 0（CLI 模式本来就不写） |

顺带确认：手工把同一帧的原话塞进顶层 `query` 再喂给 master 的 `shell_hook.py`，能正常返回记忆——检索本身没坏，只是字段没对上。

## 4. 改法

`lantai/integrations/host_protocol.py` 新增 `_hermes_shell_user_message(data)`，接在回落分支 `query or message or prompt` 的最后一位：

- 只在 `hook_event_name == "pre_llm_call"` 时读 `extra.user_message`；其他事件（含 Claude Code 的 SessionStart 等）语义不变。
- 顶层 `query`/`message`/`prompt` 仍然优先，插件和自写脚本的行为不变。
- 多模态轮的 `user_message` 是 content parts 列表，取其中的 text 段用换行拼起来；`extra` 不是对象、`user_message` 不是字符串或列表时，退回空查询，不抛。
- `session_id` 原本就读顶层，Hermes 也放在顶层，不用改。

文档两处：

- `docs/host-hook-protocol.md` §2.1 字段表补一行 `extra.user_message`。
- `docs/hermes-install-handoff.md` Step 3 原来的配法在 v0.23.1 上不生效，有两处：一是写在 `cli-config.yaml`，Hermes 不读这个文件（源码 `cli.py` 原话："no config reader loads it"；shell hook 由 `hermes_cli/main.py` 从 `load_config()` 即 `HERMES_HOME/config.yaml` 注册）；二是 `pre_llm_call:` 下面写成了映射，Hermes 要求列表，否则只报一句 `hooks.pre_llm_call must be a list of hook definitions` 就跳过（`agent/shell_hooks.py::_parse_hooks`）。改成写进 `config.yaml`、用 `- command:` 列表形式，并写明 CLI 模式只读不写、和插件只开一个（两个都开，每轮会注入两遍）。

## 5. 测试

新增 `tests/test_hermes_shell_payload.py`，7 个测试。`REAL_PAYLOAD` 取自真 Hermes 一轮实际喂给 hook 的 stdin（缩短了 id 和 conversation_history，换掉了本机路径）。

- 把 `host_protocol.py` 的修复撤掉：**4 个失败**（真实帧取到原话、多模态取 text 段、`_handle_one` 全链路把原话和 session_id 交给 `build_context`、不 mock 检索时 `log_retrieval` 真的被调用）。
- 没失败的 3 个是对照组：顶层字段仍优先、其他事件保持空查询、畸形 `extra` 退回空查询。
- 全量 pytest 结果见第 7 节。

## 6. 你自己怎么验收

1. 在 Hermes 的 `config.yaml`（不是 cli-config.yaml）末尾加：
   ```yaml
   hooks:
     pre_llm_call:
       - command: "<兰台的 python> <兰台目录>/scripts/shell_hook.py"
         timeout: 3
   hooks_auto_accept: true
   ```
   同时把 lantai-hook 插件停掉（`plugins.enabled` 里去掉），免得两边都注入。
2. `hermes chat` 问一句跟已有记忆相关的话（别用「好的谢谢」这类闲聊，会被闸门跳过）。
3. 看兰台库：`select query_text, session_id from retrieval_event order by rowid desc limit 3;`。master 上不会有新行；本分支会有一行，`query_text` 是你刚问的原话，`session_id` 是 `local-…`。
