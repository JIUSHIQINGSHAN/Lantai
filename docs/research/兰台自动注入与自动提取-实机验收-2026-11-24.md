## 三、自动注入：真机验收

### 3.1 真实 CC 会话（决定性证据）

项目级 `.claude/settings.json` 装上安装器生成的配置（`LANTAI_HOME` 指向隔离库），用 `claude -p` 起真实会话：

> **问**：你上下文里有没有『大哥的汇报偏好：先说结论再说依据』这句？
> **答**：有，原文是：「大哥的汇报偏好：先说结论再说依据，绝不先铺垫过程，中文白话不用英文状态码。」它在 UserPromptSubmit 钩子注入的【相关记忆】里，分数 0.86，对应 id mem_01M85NQNRQ0ESER0CH890SKGHZ。

> **问**：你上下文里有没有『上次会话』的五段底本？
> **答**：有，五段原文如下：1. 在做… 2. 下一步… 3. 工作区… 4. 决策… 5. 待办…（五段逐字复述）

**结论**：PR #74 的事件名修法真实有效，`SessionStart` 底本与 `UserPromptSubmit` 检索都到达模型，连 `event_id` 与分数都能复述。

| `SessionStart` 无底本 | ✅ 返回 `{}`（零侵入） | 真实库无 `session_checkpoint` 行 |

### 3.3 响应耗时（关键发现）

| 配置 | 单帧耗时 | 结果 |
|---|---|---|
| `LANTAI_INTENT_OFF=1`（跳过意图分类） | **3.7 / 4.7 / 4.9s** | 检索注入正常，带 event_id |
| 意图分类开启（默认） | **10.5 / 10.5s** | ⚠️ **撞破 8s 预算**，降级成画像兜底，**无 event_id** |

**根因**：`lantai/retrieval/intent.py:classify_intent` 每轮检索都同步调一次 LLM，本机网关实测 **11.0s**。`hybrid_search` 的 `budget_s` 只传导给 `embed`，**没有传导给 `classify_intent`**（`hybrid.py:512` 在 `t0` 之后直接调用，无 timeout 参数）。

→ 即便把 `SHELL_HOOK_TIMEOUT` 调到 8 秒，默认配置下每一轮仍会超时降级、回执链断。这是 §5.2 修法**没有覆盖到**的第三条路径。

## 四、自动提取：真实库不可用，隔离库合格

### 4.1 真实库：一提交就失败

```
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) no such table: ingest_event
[SQL: INSERT INTO ingest_event (id, created_at, ...) VALUES (...)]
```

- 代码期望 45 张表，真实库只有 42 张可对应：**缺 `ingest_event`、`conversation_message`、`conversation_job`**。
- 真实库 `user_version` 停在 v45 之前，而代码已到 v47（迁移 v46 建 `ingest_event`、v47 建会话两表）。
- `shell_hook._handle_dialogue` 捕获所有异常返回 `{}`——**宿主侧看到的是「没反应」，与「通道没开」完全同形**，无从区分。

### 4.2 隔离库：提取质量实测

四段真实文本，各自耗时与结果：

| 输入 | 耗时 | 状态 | 置信 | lane |
|---|---|---|---|---|
| 「SHELL_HOOK_TIMEOUT 从 2 秒改成 8 秒，Windows 冷启动 2.5–4.8 秒」 | 38.9s | new | 0.95 | general |
| 「我的偏好是：所有汇报先说结论再说依据」 | 33.1s | new | 0.80 | preference |
| 「笔记本是华硕天选三，RTX 3050，Python 3.12」 | 27.4s | new | 0.95 | general |
| 「今天天气不错，出门走了走」 | 24.9s | new | **0.95** | general |

**质量判定**：
- ✅ 主题词、摘要、claims/constraints/actions 字段结构完整，事实准确（「由 2 秒调整为 8 秒」「依据是 2.5 至 4.8 秒」全部正确）。
- ✅ lane 预判正确（偏好那条进 `preference`）。
- ❌ **去噪失效**：纯闲聊「今天天气不错」被提成 0.95 置信候选。`_is_chitchat` 只匹配 `NO_MEMORY_PATTERNS` 的短社交语（「好的」「谢谢」），一句完整闲聊就绕过了。
- ❌ **中文存成 `\uXXXX`**：`topic`/`claims` 字段在库内是转义序列，排查与人工审核时不可读。
- ⏱ 单条 25–39s，`SHELL_HOOK_DIALOGUE_TIMEOUT` 默认 30s——**首尾两条擦线或超时**。

### 4.3 闲聊过滤对照

| 输入 | 判定 | 结果 |
|---|---|---|
| 「好的」 | chitchat | rejected（正确） |
| 「今天天气不错，出门走了走。」 | 非 chitchat → LLM 提取 | **0.95 候选（应拒）** |

## 五、闭环链路：隔离库成立，但被同一问题挡住

```
对话提交 → 候选(new) → evolve gate → 提案(pending) → apply_proposal → memoryitem
                                                                    ↓
                                          下一次钩子检索命中并注入（score 0.85）
```

实测证据：
- 提案 `prop_01M85NN7BVN8BDGT809MAYJK38`（add, conf 0.9）→ `apply_proposal` → `memory_id=mem_01M85P2W31749MCSKT7KPHQH8N`。
- 随后 `UserPromptSubmit`「SHELL_HOOK_TIMEOUT 预算为什么改成八秒」→ 注入两条：原记忆 0.86 + **新落库记忆 0.85**，带 `event_id=rev_01M85P38DFWA36V53P3PGE770M`。

**但**：`apply_proposal` 在系统 Python 环境下同样被 chromadb 0.6.3 挡住（`to_json` 错误）。也就是说，**当前机器上提取→落库这条路整体不通**，不是偶发。

### 5.0 附带发现：钩子会对系统注入内容也发起检索

隔离库 13 条检索事件里有两条的 `query_text` 不是用户提问：

| query 开头 | session_id | zero_result | latency_ms |
|---|---|---|---|
| `<task-notification>\n<task-id>b0ewmfaed</task-id>...` | 71b11241（本会话） | 0 | 2686 |
| `jiushiqingshan D's own words (dm-ai-matrix+...)` | bb6651c8 | 1 | 2442 |

**含义**：CC 的 `UserPromptSubmit` 不只在用户打字时触发，后台任务通知、通道消息等宿主注入内容同样走这个事件。当前实现对这些内容一视同仁地跑完整检索——两秒多一次、还可能注入无关记忆（上表第一条 `zero_result=0`，确实召回了东西）。

**风险**：`retrieval_event` 表被非用户查询污染，回执链「哪轮真读了记忆」的统计口径失真；同时白耗 LLM 与嵌入配额。

**建议**：钩子侧对 `prompt` 做来源判别（如 `<task-notification>` / `task-id` 等宿主标记前缀直接 `_persona_only` 返回），或至少落事件时标记 `is_system_noise`（该列已存在）。

### 5.1 附带发现：procedural 类型渲染成 Skill

新落库记忆 `memory_type='procedural'`，注入时被渲染成：

```
## Skill: 兰台项目的检索预算参数SHELL_HOOK_TIMEOUT由2秒调整为8秒。调整 (score 0.85)
- 描述: ...
- 步骤: 1. ...
```

LLM 看到的是「技能卡」而不是「事实」。这条是既有设计（`_is_skill_item` 分支），但**自动提取产出的 procedural 记忆直接落进技能渲染面**，语义上不匹配，建议提取侧加 `memory_type` 白名单或渲染侧区分来源。

## 六、检索侧：真实库为什么零命中（两条独立原因）

### 6.1 归属过滤（265/276 条不可见）

| user_id | 条数 | 钩子可见？ |
|---|---|---|
| `api_key` | **265** | ❌ |
| `NULL` | 8 | ✅ |
| `default` | 1 | ✅ |
| `user-alice` | 2 | ❌ |

钩子调 `hybrid_search(query, top_k=..., budget_s=...)` **不传 principal** → `_converge_principal(None)` 收敛成 `user_id="default"` → 只能看到 `default` + `NULL` 共 9 条。

那 8 条 NULL 记忆内容是 `A`、`B`、`C`、「我喜欢写代码」这类测试数据——**没有任何一条真实业务记忆**。

`api_key` 的来源是 REST 侧环境变量密钥的 principal（`auth.py:149` 写死 `user_id="api_key", role="admin"`），历史上所有 HTTP 写入都挂在这个属主下。

### 6.2 verbatim 静默排除（265/276 条）

| memory_type | 条数 |
|---|---|
| `verbatim` | **265** |
| `text` | 10 |
| `fact` | 1 |

`settings.VERBATIM_IN_RECALL = False`，`hybrid.py:689`：`elif not p.verbatim_in_recall: items = [m for m in items if m.memory_type != "verbatim"]`。

→ 即便把归属修好，这 265 条**仍在最后一道被静默剔除**。两条原因叠加，真实库上的钩子检索**结构性不可能命中**。

### 6.3 向量通道版本不匹配

`chromadb 0.6.3` 建集合时 `configuration.to_json()` 不存在 → 每次检索先吃一次失败再回退关键词（实测多耗 1–2.5s），`apply_proposal` 直接抛异常。换上 1.5.9 后同一批查询 0.1–1.3s、排序准确（RRF 分 0.98/0.94/0.93）。

## 九、修复记录（同日追补，2026-11-24）

### 9.1 意图分类预算传导（P0-1）✅

**改法**：`lantai/retrieval/intent.py:classify_intent(query, timeout=None)` 接预算；
`hybrid.py` 把 `budget_s * 0.25` 传进去（余下留给 embed/BM25/组装）。超预算走
`DEFAULT_INTENT`，与 embed 预算模式同口径（一次机会即止，不重试）。

**实测对比**（同一真实帧「我的汇报偏好是什么」，`SHELL_HOOK_TIMEOUT=8`）：

| | 修复前 | 修复后 |
|---|---|---|
| 耗时 | 10.46 / 10.50s | **5.94 / 6.16 / 6.37s** |
| 结果 | 超时降级，**无 event_id** | 正常注入，带 `event_id` |

**测试**：`tests/test_intent_budget.py`（5 条，含真实调用链回归）。

### 9.2 对话通道缺表自愈（P0-2）✅

**改法**：`shell_hook._handle_dialogue` 捕获 `OperationalError` 中含「no such table」
时补跑一次 `init_db()` 并重试；仍失败返回 `{"ok": false, "error": ...}`（写路径结果
不翻译，宿主能看见失败）；其余异常仍零侵入 `{}` 但**留痕**（原先完全静默）。

**实测**（真实库副本，未动原件）：

```
命中 no such table: ingest_event → 补跑 init_db（迁移 v45→v47，4805 行 role 规范化）
→ 重试成功 → candidate_id=cand_01M85PHXV32VP1HGRB71CPHKPP，status=new
```

耗时 52.3s（含首次迁移 + LLM 提取）。

**测试**：`tests/test_dialogue_schema_selfheal.py`（3 条：自愈成功 / 重试失败如实上报 / 非 schema 异常零侵入）。

> ⚠️ **落地提醒**：真实库跑 `init_db` 会执行迁移 v45（把 4805 行 `memorycandidate.role`
> 从 `'observation'` 规范化为 `OBSERVATION`）。这是幂等的一次性迁移，但会写库——
> 建议先备份（本次已备份至临时目录）。生产服务（PID 12568）在跑时另行安排窗口。

### 9.3 钩子属主 + verbatim 开关（P0-4）✅

**真相比报告 §6 更严重**：修复属主后仍然零命中——真实库 265 条业务记忆**全是
`verbatim` 类型**，非 verbatim 的 11 条里 8 条是 `A`/`B` 测试数据。所以是**两个开关
叠加**：属主看不见 + 类型被排除，缺一条都不行。

**改法**：新增两个显式配置，**不猜身份**（沿用 `cli/mcp.py:_principal_from_params`
的既定纪律）：
