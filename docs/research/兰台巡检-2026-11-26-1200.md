## 结论

b1e94086 推上 master 后，GitHub 上 `Tests` 和 `DSH core memory` 两个工作流都是红的，失败的是同一组：`tests/test_mcp_app_browser.py` 的 3 个测试，都报 `KeyError: 'childFrames'`。原因在测试，不在产品代码：CI 用的是完整版 Chrome（`LANTAI_TEST_CHROMIUM: /usr/bin/google-chrome`），它默认开着 `IsolateSandboxedIframes`，把 `sandbox="allow-scripts"` 的 srcdoc iframe 放进独立进程（OOPIF）。页面会话的 `Page.getFrameTree` 里就没有 `childFrames`。本地没设 `LANTAI_TEST_CHROMIUM` 时，测试会先找到 Playwright 的 headless shell，它把 iframe 留在页面进程里，所以本地是绿的。

本 PR 只改这一个测试文件：先看 frame tree，有子 frame 就照旧；没有就把 iframe 当作 target 附着上去，在它自己的 CDP 会话里建隔离世界、执行脚本。产品代码一行没动。

同一份 master（b1e94086）、同一版 Chrome for Testing 159.0.8154.6：

| 浏览器 | `tests/test_mcp_app_browser.py` | 页面 frame tree 有 childFrames | Target 列表里有 `iframe about:srcdoc` |

| 完整版 chrome + `--disable-features=IsolateSandboxedIframes` | 3 通过 | 是 | 否 |

第三行说明根因就是 `IsolateSandboxedIframes`。复现命令：

```
LANTAI_TEST_CHROMIUM=<完整版 chrome 路径> pytest -q tests/test_mcp_app_browser.py
```

为什么会漏：`chromium_executable()` 在没设 `LANTAI_TEST_CHROMIUM` 时，Linux 上先找 Playwright 缓存里的 `chrome-headless-shell`，CI 却显式用 `/usr/bin/google-chrome`。两边进程模型不同，本地绿不代表 CI 绿。

## 改法

`tests/test_mcp_app_browser.py`：

- `_app_context(page)` 返回 `_AppContext(session, context_id)`。frame tree 有 `childFrames` 时照旧在页面会话里建隔离世界；没有时用 `Target.getTargets` 找到唯一的 `iframe` / `about:srcdoc` target，`Target.attachToTarget(flatten=True)` 附着，用 target id 当 frame id 建隔离世界。
- `_app_eval` 在 `_AppContext.session` 里发 `Runtime.evaluate`。新加的 `_send_in` 临时切换 `page.session`，发完换回，`chromium()` 收尾时的检查仍走页面会话。
- 3 个测试函数本身一个断言都没改。

同类检查：全仓库 grep `childFrames`、`getFrameTree`、`createIsolatedWorld`、`srcdoc`，只有这个文件用 CDP 进 iframe。`tests/test_xuanjing_mcp_app.py` 用的是 Playwright 的 `frame_locator`，它自己会处理 OOPIF，而且那个 iframe 没加 sandbox，CI 上是绿的。
