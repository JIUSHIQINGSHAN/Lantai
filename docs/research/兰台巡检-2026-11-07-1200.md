## 问题

链路（master `b2c941a0`）：

1. `scripts/shell_hook.py` `_dispatch_one` 的 QUERY 分支：`_run_with_timeout(build_context, settings.SHELL_HOOK_TIMEOUT, ..., _fallback=_query_fallback)`。
2. `_run_with_timeout`：`t.join(timeout)` 后 `t.is_alive()` 就返回 `_fallback()`，只含 `context`（常驻画像），没有 `event_id`。docstring 自己也写了「daemon 线程不可取消」。
3. worker 里的 `build_context` 继续跑完，命中路径和零命中路径都会调 `_try_log` → `log_retrieval`，落一条 `receipt_status="pending"`、`query_text` 是原话的事件。
4. 插件侧（`0295cace`）只在响应里有 `event_id` 时才挂载，`_on_session_end` 否决时才能发 `retrieval_veto`。超时轮没有 id，否决帧发不出去。
5. 300 秒后 `mark_missed_receipts` 会把它置 `missed`，但只改状态，不动 `query_text`/`query_norm_hash`。

超时不是罕见路径：`_degrade` 的注释记录了冷启动首次 import jieba/chromadb 要 0.9–1.4 秒，再加上远端 embed/rerank，2 秒硬墙在服务刚启动或网络慢时是会撞上的。而密码、密钥这类轮次是否撞上，只取决于那一刻慢不慢。

**复现（master `b2c941a0`）**：真实内存库（`param_env`），把 `SHELL_HOOK_TIMEOUT` 设为 1 秒，`hybrid_search` 换成先睡 1.4 秒的替身，用真实的 `_handle_one` 发一帧 `{"type": "query", "query": "我的银行卡密码是 864213，帮我记一下"}`：

- 响应里没有 `event_id`（宿主无从否决）。
- 约 1.4 秒后库里多出一条 `RetrievalEvent`：`query_text` = `我的银行卡密码是 864213，帮我记一下`，`receipt_status` = `pending`。

命中路径（替身返回一条记忆）结果一样。

## 修法

1. `lantai/observability/retrieval_log.py` 新增 `mark_abandoned(event_id)`：只对 `pending` 事件生效，按 `mark_vetoed` 的口径清空 `query_text`、`query_norm_hash`、`used_ids`，置 `receipt_status="missed"` 和 `receipt_at`。`result_ids`、`latency_ms`、`session_id` 等无原文元数据保留，超时轮有多慢仍然可观测。已经是 `vetoed`/`acked`/`missed` 的不改写。
2. `scripts/shell_hook.py` `_run_with_timeout` 新增可选参数 `_on_abandon(result)`。worker 跑完和主线程放弃等待在同一把锁下二选一：
   - worker 先完成 → 主线程照常拿结果（含 `event_id`），行为不变。
   - 主线程先放弃 → 返回兜底；worker 跑完后把迟到的结果交给 `_on_abandon`。
   - 不存在「主线程已经拿到 id、worker 又抹掉了事件」或「两边都不管」的窗口。
   - 回调抛错只记日志，不影响 serve 循环。
   - 不传 `_on_abandon` 的调用方（DIALOGUE、BACKFILL、VETO 等）行为不变。
3. QUERY 分支传入 `_query_abandoned`：从迟到的响应里取 `event_id`，调 `mark_abandoned`。

为什么是「抹原话 + missed」而不是「删行」或「等宿主」：宿主拿不到 id，永远不会回执也不会否决，等不到任何信号；是否被否决无法确认时，按 ADR-0084 「宁 miss 不脏写」的口径不留原文。代价是超时轮不再参与基于 `query_text`/`query_norm_hash` 的统计（缓存命中、重复问句等）。行保留，超时次数和延迟仍然能数。
