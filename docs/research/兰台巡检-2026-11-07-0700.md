## P1：插件层对 serve 子进程的读路径零超时——承诺的 5s/30s 硬超时从未接线

**在哪**

- `hermes-plugin/lantai-hook/__init__.py:18`（模块头安全边界声明）：
  「单次请求 5 秒硬超时（防卡死）；对话写入 30 秒超时（含 LLM 提取）」。
- `:92-93`：`_REQUEST_TIMEOUT = 5.0` / `_DIALOGUE_TIMEOUT = 30.0`——**全文件零引用**
  （探针证据 1：两个名字各只出现 1 处，即定义行自身）。六个 `_call_*` 全部是
  `with _lock:` 内逐字节 `proc.stdout.read(1)` 直到 `\n` 或 EOF（`:175`、`:216-221` 等），
  无任何超时机制。
- `:164-187`（`_wait_ready`）：15s 截止时间只在**两次阻塞读之间**检查——子进程活着但不吐行时，
  第一次 `read(1)` 就永远阻塞，deadline 永远轮不到判定。
- 锁放大：`_call_hook` 持 `_lock` 阻塞（`:208`），而所有其它通道与 `_ensure_proc` 都要拿同一把
  `_lock`（`:128`、`:169`）——一个 wedge 冻结全部六个通道。

**复现（`_v068_probe_r9_hook_no_timeout.py`，PASS）**

挂一个「活着但永不应答」的子进程（`python -c "import time; time.sleep(60)"`），
直调插件 `_call_hook`：

```
7s 后线程仍阻塞: True（已阻塞 7.0s > 承诺的 5s 硬超时）
PASS
```

**什么时候真的会 wedge（可达性）**

serve 进程响应各 handler 有 `_run_with_timeout` 包着（`scripts/shell_hook.py:598-651`），
但有两段在墙外：①`_prewarm()`（`scripts/shell_hook.py:738-755`）在 serve 循环开始前
建向量库连接，无超时——`launcher_mcp.py` 起 MCP 第二进程共写同库（仓库自己 Fog 里登记过的
双进程事实）时，chroma.sqlite3 的锁竞争可让 prewarm 挂起，serve 循环永不开始；
②`_wait_ready` 的就绪探测本身也走同一条无超时读路径。两者命中任一，插件侧表现完全一致：
`pre_llm_call` 回调（宿主同步调用）被无限期占用，且全局锁让 dialogue/backfill/veto/checkpoint
一并排队冻结——模块头 `:19`「任何异常绝不抛出（插件不能拖慢/搞崩 Hermes）」的约束被绕过
（不是异常，是比异常更糟的静默挂起）。

**影响**：宿主每轮对话前的注入回调可被无限期挂起；无超时、无日志、无自愈（唯一恢复途径是
外部杀进程）。与票 44（正则 ReDoS 在宿主调用链上）、票 59（O(n²) 拖死 stdio）同属
「宿主调用链冻结面」，但本条是**基础设施级**：不需要恶意输入，一次进程级 wedge 即触发。

**建议动作**：实现承诺的超时——响应等待用「写前后台 watchdog 线程 + 超时 kill 子进程」的
形态最贴合现有结构（kill 后 `read(1)` 自然 EOF 返回，既有异常路径 `:229-235` 已会把
`_proc` 置 None 触发下次重启，改动面最小）；`_wait_ready` 的就绪探测同样纳入。验收含
真实 wedge 子进程探针（本报告探针可改造成不 mock 被测链路的回归锁：AGENTS.md 测试纪律）。

## P3：勘合 `release()` 不带 claimed_at 时连 done 回执一起抹——重试语义从 replay 退化为 re-execution

**在哪**：`lantai/core/idempotency.py:267-297`。docstring（`:274-277`）写「带 claimed_at 时
只删自己那条 accepted；不删 done 回执」——但 `state != "done"` 的守卫在 `:288-292` 的
`if claimed_at is not None:` **分支内**；无令牌调用把同键**全部**行（含 done 回执）删净。

**复现（`_v068_probe_r9_release_nukes_done.py`，真内存库真勘合链，PASS）**

```
settle 后（done 回执在）: ('done', '{"ingested": true, ..., "task_id": "t1", "durable": true}')
release(无 claimed_at) 后: None
同键同文重投 claim 动作: new（done 回执在时应为 replay/t1）
对照（带 claimed_at）: ('done', ...)   ← 守卫只在带令牌分支生效，实锤
```

**影响**：显式键的 done 回执被抹后，宿主重试同键同文会重新执行整条摄取（重复建候选），
恰好是勘合模块立项时要防的原病（模块 docstring 第 2-4 行）。**缓释**：全仓 grep
`release(` 无生产调用方（纯运维面预留），接线即爆级——但运维面一旦接线就是静默数据病，
修法是三行（把 `state != "done"` 守卫移出条件分支）。同票顺带登记：`purge_expired`
（`:300-321`）每小时全量加载「超 10 分钟」的全部行（含 30 天 TTL 内的 done 回执）进内存再
Python 侧过滤，行数随时面线性增长，应在 SQL 侧按 state 分支裁剪。

## P3：MCP serve 对 notification 回错误响应——JSON-RPC 规范违反

**在哪**：`lantai/cli/mcp.py:3786-3787` 只对 `notifications/initialized` 正确静默；
其余任何 `notifications/*` 落到 `:3866-3870` 的 method-not-found 分支，回一条
`id: null` 的 -32601 错误帧。JSON-RPC 2.0 规范：notification 无 id，**服务端不得回帧**；
严格客户端会把多余响应行当协议违规。

**复现**（单行管道）：

```
$ printf '{"jsonrpc":"2.0","method":"notifications/cancelled","params":{"requestId":1}}\n{"jsonrpc":"2.0","id":1,"method":"ping"}\n' | python -m lantai.cli.mcp
{"jsonrpc": "2.0", "id": null, "error": {"code": -32601, "message": "method not found: notifications/cancelled"}}
{"jsonrpc": "2.0", "id": 1, "result": {}}
```

**影响**：低危（Claude Desktop 等主客户端容忍），但 `notifications/cancelled`（任务取消
通知）是 MCP 标准通知，随客户端成熟度提高会真实出现。同票顺带登记：`:3895-3896` 对
>1MB 行**静默 continue**——带 id 的合法请求被吞后客户端侧只会等到超时，应回 -32600/
-32700 类错误帧再丢。
