## P0 并陈——把“未决冲突”带进注入帧，不再由存储层悄悄选边（S～M）

### 动机（现状缺口）
- `lantai/cognition/context.py:778-779`：`# 4. conflicts 预留（后续接入 ConflictEngine 实时检测）` 后紧跟 `ctx.conflicts = []`——**写死为空**。而同文件 `:33` 有 `"conflicts": "## Active Conflicts"` 小节标题，`:142-150`、`:172-180` 已写好“参商抵触”的专化渲染（含樊篱 `wrap_as_data`），`routes_cognitive.py:168`、`cli/mcp.py:1541` 也都把 `ctx.conflicts` 往外送。即：**输出管线齐备，只缺数据源**，目前这一节永远不会出现。
- 库里并不缺冲突数据：`lantai/models/tables.py:453` `ConflictEvent`（`memory_id`、`incoming_ref`、`rule_name`、`kind`、`status=open/resolved/dismissed`），由 `gate/decision.py:154/186` 在规则命中时落账，`services/conflict_service.py:66 list_conflict_events` 可按 status 读取。
- 后果（推断，需确认）：一条新候选与旧记忆互斥、冲突事件处于 `open`（尚未被人或探颐裁决）期间，若旧记忆被检索进注入帧，模型看到的是“一个干净的旧事实”，完全不知道系统已经怀疑它。探颐（ADR-0037）靠主动提问求证，但只有在探针触发时才暴露；没有被动的“这条有争议”标注。
- 同类缺口：`ConflictEvent` 只存**旧**记忆 id 和新侧的文本摘要 `incoming_ref`，新侧不一定有 MemoryItem（可能还在锦囊待审），所以注入帧要展示的是“旧记忆 + 待裁决的新说法”两条文字，而不是两个 id。

### 外部依据
- *Surfacing Disagreement Beats Resolving It*，arXiv:2611.22461，2026-11-17（已打开全文 HTML）：在 LoCoMo 上做受控消融，**“把冲突集合连同来源一起交给推理方，而不是在存储层折叠成一个赢家”是 39 次运行里唯一站得住的机制**：冲突可达时 F1 +0.340（95% CI [+0.267,+0.414]），被投毒条目的攻击成功率 22/122 → 7/122（McNemar p=0.0003），token 成本几乎不变。同文发现“写入时靠图连通度打分的信任闸”在冲突可达后反而掉分（−0.075），并指出“按最近时间戳选赢家”会被控制时间戳的对手利用。注意其局限：单一模型、辩论场景、合成注入；效果依赖“冲突确实被检索到”（上限 cap 40 时只有 12/51 的冲突可达）。
- *StaleBench*，arXiv:2611.19752，2026-11-15（仅读到摘要）：多版本事实下相似度检索无法偏好当前版本。与 11-18 辨新同向，本篇不重复其评测建议。
- 同一周的 *LEDGER*（arXiv:2611.20927，2026-11-16，仅摘要）把“证据”与“答案”分开计分，可为下面的验收口径参考。

### 设计要点
1. `CognitiveContextBuilder.build` 第 4 步：取与本次入选记忆 id 相交的 `ConflictEvent(status="open")`，经 `conflict_service` 同款可见性过滤（`_visible_conflict_ids`，别绕过归属范围），按 `created_at` 倒序，最多 3 条（可由 settings 调）。
2. 渲染成现有的“参商抵触”行，补两项：`incoming_ref` 截断后的待裁决新说法，以及 `rule_name`；正文一律走 `wrap_as_data`。新增一句固定提示：“以下为未决冲突，请勿当作定论；必要时向用户求证”。
3. **只标注，不裁决**：不改检索排序、不改 `status`、不降权（降权已有 `salience_demote` 路径）。与 ADR-0084（否决回执终态）无关。
4. 默认开启与否做成 settings 开关，先 `shadow`（只记日志与 `ctx.conflicts`，不进 prompt）一轮，对比再开。
5. 选项：入选记忆没有 open 冲突，但与本次候选集内另一条同 `rule_name` 互斥时，可复用 `gate/conflict_rules.py` 做**只读**检测——这一步留给第二期，别和主线混做。

### 验收与测试
- 单测：种子库一条记忆 + 一条 `open` ConflictEvent → `build()` 的 `ctx.conflicts` 非空，`to_prompt()` 含“Active Conflicts”且 `incoming_ref` 被樊篱包裹；状态改为 `resolved`/`dismissed` 后消失；无关记忆不出现；非本人归属的冲突不泄漏（用现有 principal 夹具）。
- 回归：开关关闭时输出与现状字节级一致；`routes_cognitive` / `cli/mcp.py` 的返回结构不变（只是列表不再恒空）。
- 评测（可选，S）：复刻论文思路在 `lantai/eval` 里造 10～20 条“旧事实 + 互斥新说法（open）”样例，用同一读者比较“只给旧事实”与“带冲突标注”两种帧的回答正确率与“承认不确定”比例。**先承认这个效果在兰台、在中文、在单用户场景是否成立是未验证的**——论文是多智能体辩论。

### 风险与工作量
- 工作量 S（只读接线）～M（含评测与 shadow 观测）。
- 风险：①冲突误报会让帧里多出噪声——上限 3 条加 shadow 观测可控；②提示词诱导模型过度犹豫——验收里看“承认不确定”比例；③`incoming_ref` 是任意文本，必须过樊篱（现有渲染已覆盖，别另起一路）；④需确认 open 冲突在实际库里的存量与积压（可用 `list_conflict_events(status="open")` 先数一下，若积压很大，应先靠案牍/探颐清）。
