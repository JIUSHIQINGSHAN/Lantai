## 一句话结论

**最该先做的是「传信」：把“兰台当时知道什么”这条事务时间轴做实。** 现在 `as_of_recorded` 只按 `created_at` 近似（`lantai/retrieval/temporal.py:143` 自己写着“v2 完整版边界”），钩沉的历史语境重建（ADR-0082）用的却是**事后改写过的** `valid_to` 和**今天的**撤回状态。我在 master 上实测：60 天前记下“住在杭州”“喜欢喝龙井”，今天做一次迟到更正（上个月搬到上海）、撤回“龙井”，再问“20 天前兰台知道什么”，钩沉返回 **0 条**——两条当时都在库、都被当真的记忆一起消失，而 ADR-0082 承诺的正是“无未来污染”。

## 建议 1（P0）：传信——事务轴 as-of 做实，钩沉不再被事后更正和撤回改写

> 命名：《穀梁传·桓公五年》“《春秋》之义，信以传信，疑以传疑”。按 ADR-0013，先在 `CONTEXT.md` 登记再用。
> 承接：Maya 11-14 周报（#52）里的 DISCERN 条目只作为“弃答”依据提了一句“写入时建只增不删的双时态溯源图”；本条把它落到兰台已有的事务轴上，不涉及弃答。

### 动机（仓库里的具体缺口）

1. **事务轴只有一半。** `MemoryItem` 有事件轴 `valid_from`/`valid_to`（ADR-0048 更漏）和 `created_at`，但“这条记录什么时候被改成失效 / 被撤回”没有统一落列：
   - `lantai/retrieval/temporal.py:162-165`：`as_of_recorded` 只滤 `created_at > as_of_recorded`，注释写明“近似语义，spec §3.2 v2 边界”。
   - `lantai/cognition/late_correction.py:90-96`：迟到更正在**今天**把 `old.valid_to` 回写成**过去的**锚点，同时记了 `superseded_at = utcnow()`；但读路径没人用 `superseded_at` 去还原“更正之前的 valid_to”。
   - `lantai/services/record_ops_service.py:160-215`：`retract_memory` 只改 `status = retracted` 和 `updated_at`，**没有 `retracted_at`**（撤回时刻只在 `audit_event` 里）。
2. **钩沉的“无未来污染”承诺不成立。** `lantai/cognition/gouchen.py:236-271` 的 `reconstruct_historical_context`：
   - 查询直接排除 `status == "retracted"`，不管是锚点之前还是之后撤回的；
   - 用**当前** `valid_to` 判断锚点时是否有效，于是被事后迟到更正截断的旧值在“更正之前”的锚点也看不见；
   - `stmt.limit(limit * 3)` 没有排序，库大时取到哪些候选是随机的。
3. **撤回和失效混用了同一列。** 撤回联动原子事实时写 `lf.valid_to = now`（`record_ops_service.py:194`、`:842`），但 `late_correction.py:4` 的模块注释明确说“撤回型不设 valid_to——曾为真与从未为真语义分离”。现在撤回过的原子事实在事件轴上看起来像“到今天为止一直为真”。

### 本地实测（master `ff0166b9`，内存 SQLite，未提交）

用真实的 `apply_supersede_correction`、`retract_memory`、`GouchenEngine`：

| 步骤 | 时间 | 操作 |
| --- | --- | --- |
| 1 | 今天 −60 天 | 记入 `m_old`“用户住在杭州”、`m_keep`“用户喜欢喝龙井” |
| 2 | 今天 | 记入 `m_new`“用户上个月已搬到上海”（`event_time` = 今天 −30 天），做替换型迟到更正：`m_old.valid_to` 被回写为 −30 天 |
| 3 | 今天 | 撤回 `m_keep` |
| 4 | — | `reconstruct_historical_context(anchor = 今天 −20 天)` |

结果：`anchor-20d ids: []`。而在 −20 天那一刻，兰台实际相信的是“住在杭州、喜欢龙井”。（运行时 FTS 表和 chromadb 缺失的报错只影响索引同步，不影响结论。）

### 外部依据

- Zep/Graphiti 论文 [arXiv:2501.13956](https://arxiv.org/abs/2501.13956)：事实边同时带事件时间（`t_valid`/`t_invalid`）和事务时间（`created_at`/`expired_at`），失效是“设 t_invalid”，不是删；事务轴单独记录“系统何时得知失效”。
- [gh9ko8y/graphmemory](https://github.com/gh9ko8y/graphmemory)（2026-10-30 创建，读于 2026-11-16）：README 把双时态定义为“能回答『当时是什么』和『后来改了什么』”，原文账本 episodes 只追加不更新。
- knomit 博客 [Retraction is not deletion](https://knomit.io/blog/retraction-is-not-deletion)（2026-08-15）：在有撤回的存储里，“这条在不在”是两个问题——“截至 X 是否未被撤回”和“截至 X 最后一个可用版本是什么”，必须作为两个有名字的接口；撤回只能断言“为假”，不能断言“历史应离开语料”。
- [TARL（arXiv:2608.03699，v5 2026-09-24）](https://arxiv.org/abs/2608.03699)：把更新拆成五种可执行动作，并分别维护 accepted / pending / rejected 账本，强调“保留冲突证据、限制累积污染”。

### 设计要点

1. **补齐事务轴三列（schema v45 迁移）**：`MemoryItem` 加 `retracted_at`、`valid_to_recorded_at`；`FactAtomic` 同步加 `valid_to_recorded_at`。`superseded_at` 已有，沿用。
   - 迁移回填：`retracted_at` 从 `audit_event(action="retract")` 最近一条取；`valid_to_recorded_at` 对已有 `superseded_at` 的行取 `superseded_at`，其余取 `updated_at` 并在迁移报告里标“近似”。
2. **所有写 `valid_to` 的位置同时写 `valid_to_recorded_at = utcnow()`**：共 8 处——`late_correction.py:95/122/207`、`promoter.py:384`、`probing_service.py:714`、`record_ops_service.py:194/842/997`。建议收进一个 `set_valid_to(item, value)` 小函数，并加一条全仓扫描测试，禁止裸写 `.valid_to =`（仓库已有同类“死代码/裸写”扫描测试的先例）。
3. **撤回不再写 `valid_to`**：`record_ops_service.py:194`、`:842` 改为只写 `retracted_at` 和 `confidence = 0`，保持 late_correction 注释里“曾为真与从未为真分离”的约定。
4. **一个共享判定函数**放进 `lantai/retrieval/temporal.py`：
   - `known_at(m, t_rec)`：`created_at <= t_rec`，且 `retracted_at` 为空或 `> t_rec`，且不是 `deleted`；
   - `valid_to_as_known(m, t_rec)`：若 `valid_to_recorded_at` 为空或 `<= t_rec` 返回 `valid_to`，否则返回 `None`（当时还不知道它失效了）。
   - `temporal_view_filter` 的 `as_of_recorded` 分支改用这两个函数，去掉“近似”字样；`as_of` 与 `as_of_recorded` 同时给时，按“截至 t_rec 所知，在 as_of 时为真”判定。
5. **钩沉两种视角**：`reconstruct_historical_context(anchor_time, *, view="known_then" | "true_then")`。
   - `known_then`（默认，对应 ADR-0082“无未来污染”）：`as_of = as_of_recorded = anchor`；
   - `true_then`（“以今天所知，那时什么为真”）：`as_of = anchor`，`as_of_recorded = now`。
   - 候选查询加 `ORDER BY created_at DESC`，并把 `status != "retracted"` 改成交给 `known_at` 判定。
   - MCP / REST 的钩沉入口同步加 `view` 参数（默认值保持当前行为最接近的 `known_then`），描述写清两种视角的区别。

### 验收标准与建议测试

- 红测先行：把上面“杭州 / 龙井”场景写成 `tests/test_chuanxin_known_then.py`，`known_then` 视角在 −20 天应返回 `m_old`、`m_keep`，不返回 `m_new`；`true_then` 视角应返回 `m_new`（事件时间 −30 天起有效），不返回 `m_old`；任何视角都不返回在锚点之前已撤回的记忆。

## 建议 2（P1）：考信——接上 TimlMemBench 中文 raw-native 评测，先跑 Revoke / Supersede / Preserve 三轴

> 命名：《史记·伯夷列传》“夫学者载籍极博，犹考信于六艺”。
> 与已有建议不重复：#52 的 P2 只改 LongMemEval 弃答口径；仓库的 MemProbe 适配器只测逐字存取。

### 动机

- 兰台的卖点之一是“更正 / 撤回追踪”，但现在没有一个外部评测量过它：
  - `lantai/eval/chinese_memory_cases.py`（94 case）的类别是 typo / fresh / stale / temporal / superseded / paraphrase / typo_mid，**没有“撤回”类**，文件中“更正”“撤回”两个词出现 0 次；
  - `docs/benchmarks/longmemeval-2026-10/` 只测检索召回；
  - `scripts/memprobe_lantai_adapter.py` 文件头写明它走逐字通道，“测兰台的存储/检索保真，**不测维护行为**”。
- 你之前对 TimlMemBench 的中文“更正/撤回”评测表现过兴趣，它刚以 EMNLP 2026 Findings 发表，并公开了数据和适配协议。

### 外部依据

- 论文：[TimlMemBench: A Diagnostic Benchmark for Governed Use of Long-Term Memory in Dialogue Agents](https://aclanthology.org/2026.findings-emnlp.507)（Findings of EMNLP 2026，页 10624–10638）。208 个样本，其中中文 117 个、860 个会话、979 个问题、551 个治理用例、411 个激活用例。
- 仓库：[lyirs/TimlMemBench](https://github.com/lyirs/TimlMemBench)（读于 2026-11-16）。代码 MIT，数据 CC BY 4.0。九个诊断轴：Write、Revoke、Supersede、Preserve、Scope、Provenance、Boundary、Activation、Proactive；官方明确说“不应平均成一个总分”。
- 适配协议（`code/adapters/README.md`）：常驻进程，stdin/stdout 逐行 JSON；请求有 `reset`、`ingest_session`（按时间顺序发会话，“会话写入原生记忆管线后才回复”）、查询（raw-native 只给 `query`、`case_type`、`metrics`，不给标准答案）、`close`。响应为 `answer`（或 `<ABSTAIN>`）、`retrieved_memory_ids`、`retrieved_texts`。仓库已带 Graphiti、Zep、Mem0、MemoryOS 等 16 个外部系统的启动壳，兰台接进去就能和它们放在同一张表里比。
- 评测口径（`docs/evaluation.md`）：raw-native 测的是“系统自己从原始对话建库再作答”；论文用 `gpt-5.4-mini` 语义评审，离线冒烟可用自带的启发式评审。

### 设计要点

1. **新脚本 `scripts/timlmem_lantai_adapter.py`**，实现上面的 JSONL 协议，结构上复用 `memprobe_lantai_adapter.py` 的双闸（每个样本独立 `LANTAI_HOME`，启动器断言 ≠ 生产库）。注意票 83（评测隔离契约，`cf4804f0`、`fc4fb2c8` 刚补的红测）：新适配器必须走同一套隔离判定，不另写一份。
2. **灌库必须走对话链通道，不能走逐字通道**：`ingest_session` 把每轮交给 `lantai/ingestion/dialogue.py::ingest_dialogue`（带 `session_id`、`turn`、`created_at`），然后**同步排空**提取和演化 worker，再回 `{"ok": true}`。否则更正和撤回根本不会发生——这正是 MemProbe 适配器文件头记录的那个限制。
3. **查询**：走 `hybrid_search` 当前态视图拿记忆，`retrieved_memory_ids` 填兰台 `MemoryItem.id`；作答器用一个固定的小模型并在结果里记录模型名和日期（官方要求）。另给一个“只检索不作答”模式，用于定位是兰台检索错还是作答错。
4. **先跑三轴**：只取中文子集里 `metrics` 含 Revoke、Supersede、Preserve 的用例，先离线（启发式评审）跑通，再做一次 LLM 评审的正式跑。

## 建议 3（P2）：月令——按事实类型给“预计失效时间”，到点进“待确认”，不删除

> 命名：《礼记·月令》，按时令行事。
> 与已有建议不重复：此前各份建议都没涉及按类型的有效期。与建议 1 的关系：本条只产生“预计”，不写事实轴；需要建议 1 先把事务轴理顺。

### 动机

- 兰台现在的“过时”只有两种来源：显式更正（late_correction）和衰减归档。衰减是“重要度”维度，不是“是否还为真”：
  - `lantai/memory/forgetting.py:173-185`：只有 working 层按 `WORKING_MEMORY_TTL_DAYS = 60`（`lantai/core/settings.py:74`）一刀切归档；
  - `MemoryItem.decay_class`（`tables.py:151`，procedural / semantic / episodic）管的是衰减快慢；
  - ADR-0081 知命的半衰期也是置信度衰减。
- 结果是“我今天在开会”“这周在出差”这类**本来就有时效**的话，没人更正就会一直以当前事实注入，只是分数慢慢下降。

### 外部依据

- [gh9ko8y/graphmemory](https://github.com/gh9ko8y/graphmemory)（读于 2026-11-16）README 的“时间梯度与 TTL”：写入时按内容分类定有效期——临时状态（现在/今天/在忙/心情）1 天、动作/失败 3 天、事件 7 天、无日期承诺 10 天、普通事实 14 天、偏好永久（被新事实覆盖才失效）、身份陈述 3 年、不可更改事实（性别/出生/籍贯/亲属）永久；有明确日期的约定不设 TTL，“到日期进入『待确认』”；到期后先隐藏，原文账本永久保留。这正是你之前感兴趣的“双时态事实 + 按类型 TTL”。

### 设计要点（兰台化，比 graphmemory 保守）

1. **不写 `valid_to`，另加 `valid_to_expected`**（可与建议 1 同一次迁移）：TTL 是推测，不是记录到的事实；写进 `valid_to` 会污染建议 1 刚理顺的事件轴。
2. **规则优先的中文分类器** `lantai/cognition/yueling.py`：按时间词（“现在/今天/这会儿/这周/最近”）、情绪词、动作完成体、承诺句式（“答应/约好/下周X”）分类；能解析出明确日期的承诺，`valid_to_expected` = 该日期 + 1 天。分类结果写进 `structure["yueling"]`，便于审计。偏好、身份、procedural 一律不设。
3. **到期不删、不归档，只降级注入**：注入组装（`scripts/shell_hook.py` 与 MCP context）遇到 `valid_to_expected < now` 的记忆，加“（记于 X，可能已过时）”标注并降到末位；有明确日期的约定到期后进入知命的 `weakened`，等用户或对话证实再恢复（复用 ADR-0081 的 `rejuvenate`）。
4. **TTL 表放 settings**，默认值参考 graphmemory，但第一版只启用“临时状态”和“有日期约定”两类，其余观察一段再开。

### 涉及文件与改动范围
