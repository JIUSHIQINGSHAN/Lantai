# 每日建议 2026-11-28

> 调研基线：master `2cf211e4`（v0.70.0 悬镜，schema v49，ADR 最新 0099）。
> 承接：2026-11-27 的 PR #85（返璞）末尾提到"法门与 errsig 是这类探针的对象"；本条把法门本身补上"会过期、会被事实推翻"的一环。与 #85、#83 不重叠。

## 一句话结论

法门（`lantai/cognition/famen.py`）匹配只看词袋重合，完全不看这条 SOP 是否还灵：本地实测，一条 12 次命中、2 次成功、9 次失败、400 天没评估过的"日历技能"，仍以 9.18 分被匹配出来，`confidence` 恒为 1.0，失败次数连输出里都没有。11-16 的新论文 *Experience Rot* 恰好证明这类"曾经正确、后来失效"的程序性记忆比没有记忆还糟。建议给法门加"鉴旧"：把已有的成败计数用起来、给 SOP 加最后验证时间、在注入时标注，不删不改写。

## P0 鉴旧——法门匹配纳入成败与新鲜度，并在注入帧标明"上次验证于何时"（M）

### 动机（现状缺口，含本地实测）
- `lantai/cognition/famen.py:385-404` 的 `_crystal_asset` 把 `confidence` 写死为 `1.0`，`metadata` 只带 `hit_count` 与 `success_count`，**不带 `failure_count`、`last_evaluated_at`、`updated_at`**。同一表 `SkillCrystal`（`lantai/models/tables.py:402-407`）里这几列都已存在，由同袍的 `record_shadow_result`（`lantai/cognition/tongpao.py:354-381`）累加，但法门不读。
- `match_skills`（`famen.py:569-625`）的得分只由名称、触发规则、步骤的词重合构成；排序键是 `(-score, -confidence, id)`，而 `confidence` 对结晶恒为 1.0，等于没有。
- `_memory_asset`（`famen.py:407-430`）来源的 SOP 连成败计数都没有，只有 `created_at`。
- 注入渲染（`lantai/cognition/context.py:353-380`）只输出名称、触发、步骤等，没有任何"多久前验证过、成败比"的信息，Agent 与用户都无从判断这条 SOP 是否还可信。
- **本地实测**（内存 SQLite，临时测试已删除，未提交）：插入一条 `approved` 的 `SkillCrystal`——`calendar-schedule-event`，步骤写 `payload 里用 attendees 字段`，`hit_count=12, success_count=2, failure_count=9`，创建与更新时间均为 400 天前。调用 `FamenEngine(session).match_skills("帮我安排一个日历 calendar event 会议")`，结果：命中，`score=9.18`，`confidence=1.0`，`metadata={'hit_count': 12, 'success_count': 2}`，返回字段里没有失败数与新鲜度。这就是"失败多于成功的旧 SOP 仍排第一且满分可信"。

### 外部依据（均已打开页面）
- Xu 等，*Experience Rot: Experienced Agents Fail Where Novices Succeed*，arXiv:2611.20922，2026-11-16：工具接口悄悄变化后，带着旧经验的 Agent 在多数任务上失败，而无经验的 Agent 多数成功；"在不完整文档下，过期经验的成功率 23%，远低于无经验的 63%"；在所测的各种记忆形态（对话、记忆文件、检索记忆、技能脚本）里都出现，经验越多越严重；失败后 347/348 例仍向用户报告"已完成"。给记忆打版本号、告知"服务已更新"几乎没用（成功率 46%→50%）；有效的是写后读回校验（成功率到 91%，调用数翻倍多）和让写入返回已存对象（45%→79%）。作者的结论是"记忆系统需要有办法发现已存的用法不再成立"。https://arxiv.org/html/2611.20922v1
- MEME，*Multi-entity & Evolving Memory Evaluation*，arXiv:2605.12477v2，2026-11-11 修订：六个记忆系统在依赖推理上整体塌陷（Cascade 3%、Absence 1%），说明"记忆里的某条变了，依赖它的另一条怎么办"目前没人做好。https://arxiv.org/abs/2605.12477v2
- 同文给出的限制要如实带上：Experience Rot 的服务是合成的小服务，模型是其自选的六个，且作者没有测"为什么 Agent 不再检查"；所以它支持的是"需要一个发现陈旧的机制"，不是"某个具体阈值有效"。

### 设计要点
1. **读已有列，不加新列（第一步）**：`_crystal_asset` 的 `metadata` 补 `failure_count`、`last_evaluated_at`、`updated_at`；`confidence` 改为由成败派生：`(success + 1) / (success + failure + 2)`（拉普拉斯平滑，样本少时接近 0.5，不会因一次失败就清零）。`_memory_asset` 无成败列，先只补 `age_days`，不编造置信度。
2. **匹配分乘一个有下限的折扣，而不是硬过滤**：`final = score * max(0.3, confidence)`；`failure_count >= 3 且 failure_count > success_count` 时标 `stale_suspected=True`，仍返回但排序靠后。宁可降位并标注，不静默丢弃（沿用"关闭未合/降权"的保守习惯，也避免误伤刚坏一两次的好 SOP）。
3. **注入标注**：`context.py` 渲染法门时在每条后附一行 `（成 2 / 败 9；上次验证 400 天前；疑已失效，执行前请核对当前接口）`，文字走现有 `wrap_as_data`，不新增可注入面。Experience Rot 的结论是"附在请求旁边的提示才被看见"，所以放在步骤正文紧邻处，不放系统提示里。
4. **执行后回写入口（可放第二步）**：目前只有同袍的影子评考会累加成败。给 `famen_skill` 的 MCP 工具加一个可选的 `outcome` 回执（`success|failure`），复用 `record_shadow_result` 的累加逻辑与属主校验；不改默认行为，缺省不回写。这样日常使用也会让陈旧 SOP 暴露出来。
5. 新增 ADR 先登记名称：建议名"鉴旧"（出自"温故知新"一类说法，须按 ADR-0013 先入候选池；本仓 CONTEXT.md 与 docs/adr 未发现占用）。编号接 ADR-0100。

### 涉及文件与范围
- `lantai/cognition/famen.py`（`_crystal_asset`、`_memory_asset`、`match_skills` 的折扣与标记）
- `lantai/cognition/context.py`（法门切面的渲染行）
- `lantai/cli/mcp.py` 与 `lantai/services/famen_service.py`（仅第 4 点的可选 `outcome`，且须同步 MCP 工具 schema 与 80 工具池一致性守卫）
- `docs/adr/0100-*.md`、`CONTEXT.md`、`CHANGELOG.md`
- 不改表结构、不动迁移（schema 仍 v49）；不改默认检索与衰减。

### 验收与测试
- 复现上面的实测作为回归：`success=2, failure=9` 的结晶，`confidence < 0.3` 被下限抬到 0.3 参与折扣，`stale_suspected=True`；同样文字、`success=9, failure=0` 的另一条排在它前面。
- 样本不足不误伤：`success=0, failure=1` 不标 stale。
- 渲染：注入帧含"成/败/上次验证"，且整段仍在 `<memory_data>` 围栏内，对含 `</memory_data` 的恶意步骤正文做一次樊篱回归。
- 属主：A 的 `outcome` 回执不能改 B 的结晶（沿用 tongpao 的 `_get_crystal_for_shadow` 校验）。
- 现有 `tests/test_famen_engine_smoke.py`、`test_famen_api_smoke.py` 全绿；这两个文件用的结晶默认 `hit_count=1, success_count=0, failure_count=0`，需确认默认折扣不会把它们压到 `score<1.0` 的门槛以下（实现时优先保证零成败时不折扣）。

### 风险与工作量
- 风险：折扣系数与 3 次失败的门槛是启发式，没有数据标定；先只标注、折扣下限定为 0.3，并在 ADR 里写明"未校准"，后续可用 #83 的无记忆对照或 #85 的消融来标定。回执入口会增加写面，须限定身份。
- 工作量：第 1～3 点 S～M（约 1 天）；第 4 点 S；总体 M。

## P1 复核钩——SOP 步骤里引用的工具名，与当前 MCP 工具表对不上时，标"疑失效"（S～M）

承接：P0。Experience Rot 的核心场景是 Agent 照旧经验调用已改名的工具字段；MCP 侧同期也在变：规范把 Tasks 移出核心、做成官方扩展（SEP-2663），并在 2026-07-28 版把服务端主动请求改成多轮往返（MRTR，SEP-2322），下一版目标 2027-03-30（https://modelcontextprotocol.io/specification/2026-07-28/changelog 、https://modelcontextprotocol.io/development/roadmap ，均已打开）。工具接口变化会越来越常见。

### 动机
- 法门 SOP 的步骤是自由文本（`_extract_sop`，`famen.py:275-330`），可能写着 `调用 foo_bar`、`字段 x`。兰台自己在 `lantai/cli/mcp.py:4440` 已经掌握当前 `tools/list`，但法门与工具表之间没有任何对照。
- 未实测；以下为设计推断，实现前需先在样例上验证抽取召回。

### 设计要点
1. 在渲染法门时，用正则从步骤里抽出形如 `[a-z][a-z0-9_]{3,}` 的候选工具名，与当前注册的工具名集合求交；对"看似工具名、却不在当前集合"的，附一行"步骤引用的 `xxx` 不在当前工具表，执行前请核对"。只提示，不改内容。
2. 只对兰台自家 MCP 工具表有把握；宿主侧（Claude Code、Hermes 等）的工具表兰台看不到，所以只检查兰台自己的工具，宿主工具不报。这一限制要写进文档。
3. 误报风险：普通英文单词、变量名会被当成工具名。需要白名单（已知非工具词）与"必须含下划线"的收紧条件。

### 验收与测试
- 样例：步骤含已废弃的旧工具名 → 标注；含当前工具名 → 不标；含普通蛇形变量（如 `max_retries`）→ 不标（靠"必须匹配兰台工具名前缀"或白名单）。
- 对仓库内现有法门测试样例零误报。

### 风险与工作量
- 风险中：误报会让 Agent 对好 SOP 起疑。建议先放在 `--diagnose` 类只读诊断里跑一周看误报率，再决定是否进入注入帧。S～M。

## 不建议现在做
- 不要用"写后读回"强制每条 SOP 执行后校验：Experience Rot 显示它有效，但调用数翻倍；兰台不控制宿主的执行循环，做不到。
- 不要把版本号标签贴到 SOP 上当作主要手段：同文实测几乎无效（成功率 46%→50%）。
- 不要现在跟进 MCP 的 Tasks/MRTR 改动：兰台是 stdio 工具服务，下一版规范 2027-03-30 才落地，先观察。
