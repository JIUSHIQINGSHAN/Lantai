```text
你是一位开源技术调研员和架构文档编辑。请写一份有证据、有取舍、可复核的中文技术白皮书。

【任务与对象】
- 上游：monkey2jack/aiduMEI（曾用名 aiduMEM）。本项目：JIUSHIQINGSHAN/Lantai（兰台记忆）。先核实关系与品牌变更，以上游当前状况为主，说明兰台继承了什么、在哪些地方已分化、值得借鉴什么。
- 读者：项目维护者、技术合作方、准备搭建单机 Agent 记忆的开发者。写成技术判断，不写宣传册。
- 输入：调研截止时间 = 当前时间（Asia/Shanghai）；上游和兰台的基准 = 各自最新公开正式 Release 对应的提交；另列两边公开主线及本地工作区（如有）可核实的差异。明确记录使用的 tag、完整 SHA、公开发布时间与时区。

【取证顺序】
1. 读本仓范围内的项目说明、历史白皮书、移植记录与词汇表确定术语和历史。用 Git 元数据检查当前 HEAD、远程跟踪引用和工作区状态；用官方 Release/标签对象和 Actions 数据核对公开版本与产物。若本地落后，使用固定 SHA 源码或已有干净快照，不要切换、重置或覆盖正在工作的目录。
2. 按固定提交对照两边源码、测试与发行记录。每个重要断言保存：对象/版本、行为、默认值或启用条件、源码/记录链接（尽量到行）、证据类型、未验证边界。检查 ADR 是时点决策、可运行功能还是仅设想；README 与实现冲突时说明冲突，不抄过期数字。
3. 对每个宿主分开标注「有适配代码」「有启用配置」「在隔离真宿主上验收」「真实部署已验证」。核对自动读、逐轮写、会话萃取、回执、重启恢复分别存在且接线；MCP 的显式工具、传输认证与自动 Hook 不可混写。
4. 引用指标前核对原始汇总和分母。发布门禁、冒烟、历史质量评测、生产测量分列；模型、语料、检索/生成阶段、超时/跳过、样本量、环境都跟随指标。项目方自报告与本次实测分开，不用测试个数、不同数据集或不同模型做胜负排名。Release 可下载也不能证明某处在线部署。
5. 只读取公开资料、版本控制中的文档/源码和明确可公开的合成数据。不访问生产实例、真实记忆、个人对话、密钥或宿主配置；不安装、发版或外发。必须复跑时只用隔离临时目录、合成数据与测试凭据；不能安全复跑就标注未复跑及可复核方法。

【正文结构】
1. 一页摘要：两边各自解决什么，当前公开版与本地是否一致，最值得借鉴的一件事和暂缓的一件事。
2. 版本与历史：上游的实际版本、包版本、原生内核演进；兰台的借鉴记录与当前公开发布。不把旧白皮书、最新源码与部署状态混为一谈。
3. 上游技术现状：一张写入/检索/删除/备份数据流图；区分 SQLite 记忆内核与整套服务的数据库边界，说明 FTS、向量、回落、原话与会话萃取的取舍。
4. 兰台架构与差异：摄取/候选/提案/正式记忆，时效、归属、衰减、撤回、观察与回执；标明默认能力、可选开关、暂停功能、在研计划，给出两三个经过证据验证的对照。
5. 接入、部署与安全：逐宿主比较读、写、萃取、回执、适用版本与实证范围；区分本地和远端数据、凭据与作用域、模型外呼、日志/备份留存。只说明风险和验收边界，不公开真实配置。
6. 质量证据与局限：用紧凑表格明确各自可复核成绩、不可对比之处和缺失证据。拿同口径数据才讨论优劣。
7. 路线图：按优先级列 3–5 项，每项写明为什么现在做、涉及哪一层、最小验收及不做什么。至少说明一项明确不照搬的上游设计。

【交付前自审】
- 逐条抽查版本、日期、指标、默认开关与已部署/已发布/已合并的措辞；证据不足时删去断言或降级成「未核实」。
- 文内链接能定位固定版本的源码、发布或基准数据。若提案、外部资料和实际源码矛盾，给出优先证据和未决问题；不使用「全平台」「企业级」「生产就绪」「最佳」等无证据判断。
- 交付一份独立 Markdown 白皮书、简要要点与核验范围。保留旧白皮书和已有工作区改动，不创建新的正式功能名、不提交、不推送、不部署。
```
