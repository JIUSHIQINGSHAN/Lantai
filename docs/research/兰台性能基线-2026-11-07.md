## 1. 结论速览

1. **本地管线在 5000 行库容下全链 60-70ms**（检索/注入/摄取 P50），FTS 通道亚毫秒——
   「慢」不在本地管线，端到端延迟的支配项仍是一次真实 embedding ~2s（v0.15.2 基线结论，本轮替身化后再次单列证实）。
2. **p95 对 2s 注入硬墙的余量：常温 17-73 倍**（详见 §5）。余量吃紧只发生在
   「全量 pytest 后段 + 常驻服务争 CPU」这类数量级负载退化下——这正是
   `build_context` 2s 超时 flaky 的触发条件（假说已验证，见 §6）。
3. **头号热点**：向量通道 ACL `$or` 归属过滤令 chromadb 0.6.3 元数据层全表扫
   （带过滤 50.7ms vs 无过滤 3.0ms @5000 行，17×），读路径与摄取路径共同的热点（§7 H1）。
4. **MCP serve 通道**（2026-11-08 补测）：通道本体（stdio 管道 + JSON-RPC）底价
   ping 0.2-0.4ms，可忽略；端到端成本的大头是 handler 附加面——其中
   `build_cognitive_summary`（认知摘要）随库容近线性增长（10.3ms@1000 → 41.2ms@5000），
   是本轮新点名热点（§4、§7 H7）。

机器：Intel Core i5-12500H（12 核 16 线程）/ 15.6 GB RAM / Windows 11，单线程顺序执行。

| 项 | 值 |
|---|---|
| Python | 3.11.15（项目 `.venv311`；仓库根 `.venv` 是 py3.14 且无 chromadb，**复现勿用**） |
| SQLite | 3.53.1（stdlib sqlite3，FTS5 + trigram） |
| 向量库 | 生产同款内嵌 ChromaDB 0.6.3（HNSW-cosine），临时目录 |

**口径纪律**：进程内直调核心函数，自建临时 SQLite（真实建表 + 全量迁移链 + FTS5 trigram
+ 灌种子化合成语料），跑完自清理，绝不读写宿主真实库。外部服务面用确定性替身并**单独计量，
不与本地管线混账**：

| 外部面 | 处理 | 依据 |
|---|---|---|
| embedding API（bge-m3） | 确定性哈希嵌入替身（128 维），替身自价单列 `embed_fake_cost`（0.02-0.05ms，不构成噪声底） | v0.15.2 基线实测 ~2s/次，网络 RTT 支配端到端 |
| LLM 提取/意图 | 确定性 JSON 应答替身；意图分类 `LANTAI_INTENT_OFF=1` 走本地规则 | 外部 LLM |
| reranker | 关（settings 关档） | 外部服务 |
| 向量库 | 生产同款 ChromaDB（装不上自动降级纯 Python 替身并声明） | 本环境可用 |

健全性自检内置（`sanity_check`）：三召回通道必须有货、build_context 必须真走到检索、
fastpath 必须真命中白名单、MCP 场景每次调用必须真命中——不满足直接拒绝出报告。

## 4. MCP serve 通道（2026-11-08 补测）

`mcp_serve_search` 场景：spawn 真实 stdio JSON-RPC 子进程（`lantai/cli/mcp.py:3874 main()`
标准主循环，默认档 `HERMES_CORE_TOOLS`），经环境变量指向同一临时库、补与父进程同源的
确定性嵌入替身，端到端计时宿主典型请求 `tools/call search`。

**通道元数据**（一次性开销）：

| 项 | 1000 条 | 5000 条 |
|---|---|---|
| 冷启动 spawn→initialize | 1411.8ms | 1470.8ms |
| 首查（含子进程 chromadb 装载） | 1079.0ms | 1123.4ms |
| ping 通道底价（5 次中位） | 0.39ms | 0.234ms |

**稳态往返**：P50 29.40ms / P95 52.85ms @1000；P50 166.07ms / P95 239.80ms @5000。

**分解实验**（父进程内直调 handler 及其分量，对照 hybrid 本体；P50，ms）：

| 分量 | 1000 条 | 5000 条 |
|---|---|---|
| `hybrid_search` 本体 | 31.98 | 111.21 |
| `handle_search`（MCP 全链） | 49.63 | 158.34 |
| ├ `build_cognitive_summary`（`lantai/runtime/middleware.py:28`） | **10.34** | **41.16** |
| ├ `log_retrieval` 检索事件落库 | 6.75 | 5.68 |
| └ `build_evidence` / 围栏包裹 / JSON 序列化 | ~0 | ~0 |

归因：**通道本体可忽略**（ping 底价 0.2-0.4ms，占往返的 0.1%-1.4%）；MCP 端到端
相对检索本体的增量来自 handler 附加面，其中认知摘要占大头且**随库容近线性增长**
（10.3→41.2ms，5× 行数 ≈ 4× 耗时），5000 档约占端到端往返的 1/4——见 §7 H7。

测不准注记：1000 档实测往返（29.4ms）低于父进程 `handle_search` 直调（49.6ms）——
子进程是干净进程（无父进程连跑多场景累积的 GC/内存压力），且分解实验与基准轮相隔
数分钟、共享机有并行负载抖动。**分解数字与往返数字不逐项硬配平**，按量级结论采信。

## 5. p95 对 2s 硬墙的余量（最关键结论）

墙的位置：`SHELL_HOOK_TIMEOUT: int = 2`（秒，`lantai/core/settings.py:274`），
`build_context` 经 `_run_with_timeout`（`scripts/shell_hook.py:674`）受此硬墙约束，
超时走 `_query_fallback` 降级（常驻画像仍在，检索段丢弃）——**降级本身是设计行为**
（宁降级不崩，D-04 票口径）。

build_context 的 p95 与余量（以 11-07 正式轮为准）：

| 库容 | p95 | 对 2000ms 的余量 |
|---|---|---|
| 1000 条 | 27.3ms | **73×** |
| 5000 条 | 85.5ms | **23×** |
| 5000 条（复验轮，磁盘抖动日） | 116.0ms | **17×** |

**结论**：常规注入负载下余量充分（最低实测 17×）；余量吃紧需要**数量级**的负载退化，
不是渐进变慢能撞到的——实测到的退化源只有一个：「全量 pytest 后段（数千测试累积进程
重载）+ 开发机常驻服务竞争 CPU」，即测试基建负载，不是生产注入负载。生产侧需要留意的
只有两点：库容持续线性增长（p95 口径 ~0.017ms/行，5000 行 85.5ms 实测外推）与检索事件
同步落库的磁盘抖动敏感性（复验轮 +14% 的主因）；前者在 5 万行时把 p95 推到 ~850ms 量级、
余量缩到 ~2.3×，届时应先做 §8 的 H1。

## 6. flaky 假说验证

**假说**（`.scratch/watch/build-context-2s-timeout-flaky.md`，本地件）：`build_context`
走 `_run_with_timeout` 2s 硬墙，全量 pytest 后段高负载下擦线超时 → `_query_fallback`
降级 → 测试 mock 的 `log_retrieval` 从未被调用 → 测试报 AttributeError。

**判定：已验证成立**（机制链全实锤，非本会话复现，来自 2026-11-07 当日的最小实验并
已收口）：

1. **复现实验**：把 `SHELL_HOOK_TIMEOUT` 压到 0.001s 单跑，复现与全量后段完全相同的
   失败签名（`m.call_args` 为 None → AttributeError）——根因链闭合（commit `1c7c7ab6`）。
2. **本基线的增量贡献**：量化了「擦线」的含义——常温 p95 余量 17-73×（§5），说明触发
   超时需要的不是百分之几的漂移，而是测试全量后段那种数量级的 CPU 争用；这与历轮
   「全量 4:51-17:00 耗时抖动 3.5 倍」的负载区间自洽。
3. **处置已落地**：透传语义测试与墙宽解耦（放宽墙宽 + 超时降级行为由
   `test_hook_timeout_budget.py` 专门验证），全量偶发失败消除；生产行为（超时降级、
   画像保留）本身正确，无需改动。

如实声明：本会话**未**重跑全量负载刻意复现该 flake——留档的最小实验已闭环同一根因链，
为复现而制造 17 分钟全量负载收益为零；且票 04（`.scratch/v068-perf/issues/04`，本地件）
记录的 Temp 并发清扫 flake 是另一独立环境级问题，与本假说无关。

### 热点清单（对照实验数据）

- **H1 🔴 向量通道 ACL `$or` 过滤 = chroma 元数据全表扫（17×）**：
  `lantai/core/acl.py:94 (vector_owner_filter)` 对非 admin 一律包
  `{"$or":[{"user_id":viewer},{"user_id":""}]}` → chromadb 0.6.3 对 metadata **逐行物化
  全表**（5000 行库每次查询 ~50630 次 lambda），HNSW 索引对带 where 查询不参与预过滤。
  对照实验：同库同查询带过滤 50.7ms vs 无过滤 3.0ms。读路径（hybrid/build_context）
  与写路径（摄取去重 `_apply_dedup`，`lantai/services/memory_service.py:80`）共同热点。
- **H2 🟠 chromadb otel 遥测包装器**：每次段方法调用包 span（5000 档 50780 次，cum 690ms），
  `anonymized_telemetry=False` 关不掉；随 H1 消解，或随 chroma 1.x 升级复核。
- **H3 🟠 每次检索附带完璧原子事实反查**：`lantai/retrieval/hybrid.py:980` →
  `wanbi_retriever.py:117`，~2.5ms/次，纯增量、随 fa 表增长。
- **H4 🟠 检索事件同步落库**：`lantai/observability/retrieval_log.py:53 (log_retrieval)`，
  ~6-7ms/次注入（序列化 + INSERT + commit），占 build_context ~10%，对磁盘抖动最敏感
  （复验轮 build_context +14% 的主因）。
- **H5 🟡 apply_forgetting 全表扫**：`lantai/memory/forgetting.py:87`，0.37ms/行；
  5 万行冷扫约 18s，此前不必动。
- **H6 🟡 apply_proposal 3 commit + 1 chroma add**：单次平坦；批量演化时 commit 合并是显见优化点。
- **H7 🟠（本轮新增）MCP search 的认知摘要附加面**：`lantai/cli/mcp.py` 的 `handle_search`
  每次调用 `build_cognitive_summary`（`lantai/runtime/middleware.py:28` →
  `lantai/runtime/runwu.py:84 extract_summary`），10.3ms@1000 → 41.2ms@5000（近线性），
  5000 档占 MCP search 端到端 ~25%。宿主不传 `task` 时以 query 兜底构建，**每次检索都付这笔税**。

## 8. 改进建议（按数据排期）

1. **P0 — 向量通道 ACL 过滤方式重审**（H1，17× 劣化、占读路径 4 成以上）：三个方向需
   独立票据权衡——chroma 侧先取 top-N×margin 再在 lantai 侧后过滤（快，但高异质库有漏
   召回风险，需按「宁 miss 不脏写」论证）；升级 chromadb 1.x（同步消 PYSEC 三个 CVE）
   验证 where 是否走索引；把归属过滤上移到 `_query_items` 兜底层（三通道并集后已二次过滤，
   语义不变）。
2. **P1 — MCP 认知摘要条件化/缓存**（H7，41ms@5000 且随库容增长）：按 `task` 参数显式
   传入才构建，或按 (task 哈希, user) 短 TTL 缓存。注意这是 v0.4 特性语义，改动需票据评估
   对注入质量的影响——数据只支持「它贵」，不支持「它没用」。
3. **P1 — RetrievalEvent 异步化**（H4，6-7ms/注入、磁盘抖动放大器）：复用 telemetry
   writer 后台线程落库，注入路径只入队；崩溃窗口按「宁 miss 不脏写」落 pending→missed。
4. **P2 — 摄取去重限近端窗口**（H1 写侧）：`_apply_dedup` 先 `content_hash` 精确短路
   （票 02 已修一半），再退化到向量相似或限最近 N 条/同 lane，把摄取从 O(库容) 拉回 O(1)。
5. **无需优化（如实排除）**：FTS5 两通道（亚毫秒/3.4ms）、闸门/意图本地分类/RRF 合并
   （微秒-低毫秒）、apply_proposal 单次（13ms 平坦）、apply_forgetting（5 万行前不动）。
   外部 embedding（~2s/次）仍是端到端支配项——上述优化只在「网络预算传导砍掉向量通道」
   或「库容持续增长」场景有体感，排期应与 embedding 缓存/批量化一起看。

## 9. 复现

```bash

python scripts/perf_bench.py --scale 1000 5000 --profile \
  --out .scratch/v068-perf/artifacts/<run-name>

```

`--profile` 同时把原始 `.pstats` 落 `--out` 目录（`<规模>-<场景>.pstats`，pstats.Stats 可
交互复盘）。MCP 场景的通道元数据（冷启动/首查/ping）在 baseline.json 的 `mcp_channel` 字段。

## 10. 没能测到 / 测不准（如实清单）

1. **MCP 写通道未测**（`add` / `add_dialogue`）：子进程与父进程并发写同一 SQLite/chroma
   会混入锁等待，测出的不是通道时延；写路径成本由进程内 `ingest_add_memory` /
   `ingest_fastpath` 口径覆盖（62.9/61.9ms @5000），通道附加面按读路径实测 <1% 类推。
2. **MCP 往返与分解实验不严格配平**（1000 档往返 29.4ms < 直调 49.6ms）：共享机并行
   负载抖动 + 干净子进程效应，按量级结论采信，不逐项硬配平（§4）。
3. **2026-11-08 复核轮绝对值不可跨日对比**：当日共享机并行会话负载使全场景 +80-130%；
   跨日对比以 11-07 正式轮为准，两轮代码与种子完全一致（§3）。
4. **并发/多用户负载未测**：票据明确非目标；单人部署为主。
5. **chromadb 1.x 的 where 过滤性能未测**：本环境 0.6.3；升级验证属票 03（H1 选型）范围。
6. **真实 embedding/rerank/LLM 延迟未测**：外部服务，沿 v0.15.2 结论（~2s/次支配端到端）。
7. **apply_forgetting 冷扫方差大**：2 迭代含首扫归档写入，336→449ms@1000 的口径方差；
   只看量级。
8. **MCP 冷启动/首查为单次采样**：受磁盘缓存与杀软扫描影响大（1411-1471ms 区间外无
   分布数据），只给一次性实测值。
9. **cProfile 不跨进程**：MCP 子进程内部热点未单独剖析，其附加面由父进程内分解实验定位
   （§4）；如需子进程内热点，需给子进程挂 `--profile` 引导，属后续可选工作。
