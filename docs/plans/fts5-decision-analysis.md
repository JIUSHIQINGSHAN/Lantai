## 一、现状盘点（代码事实，非印象）

| 事实 | 证据 | 含义 |
|------|------|------|
| `init_fts` 建表被调用 | `storage/db.py:16` | FTS5 虚拟表随 init_db 创建，**表存在** |
| `index_fts` **零调用方** | grep 全仓仅 fts.py 自身 | 从未有记忆写入 FTS 索引 |
| `search_fts` **零调用方** | grep 全仓仅 fts.py 自身 | 检索主链路从不读 FTS |
| 检索主链路 | `hybrid.py`：向量(Chroma) + BM25(jieba) + 衰减 + 可选 reranker | FTS 完全不在其中 |
| MemoryItem 创建点 | `promoter.py:48`（apply_proposal add 分支）唯一 | 接入 FTS 的写入同步点集中 |
| 更新/回滚/删除点 | `promoter.py` update 分支、rollback、delete_memory | 共 4 处需同步 |
| 当前打分权重 | `hybrid.py:118`：0.6 向量 + 0.3 BM25 + 0.1 衰减 | BM25 是关键词层唯一来源 |
| 测试 | `tests/test_p0.py` TestFTS5 4 个单元测试（v0.3.2 重写后全绿） | 接入后测试可直接复用 |
| 数据规模 | remembrance.db ≈ 184KB | 个人记忆系统，千-万级，FTS/BM25 均非瓶颈 |

**结论先行**：FTS5 是一段"建了表、修好了 schema、配好了测试，但从未通电"的代码。这正是审计判定的死代码。

## 二、FTS5 trigram 对中文记忆检索的真实价值

系统面向中文记忆。当前关键词层是 **jieba 分词 BM25**，其特性：
- ✅ 词级精确匹配，2 字词（"学习"）表现好
- ❌ **错别字零容错**（"向量" vs "向良"）
- ❌ **子串匹配弱**（"检索方案" 查 "索方案" 的错位输入）
- ❌ **每次查询全量重建语料**（`hybrid.py:106-107` BM25Okapi(corpus)），数据量上来后是 M4 性能项

FTS5 + trigram 的特性：
- ✅ 3-gram 子串匹配，对错字/插入/删除有天然容错（"学习机"能撞上"学习"）
- ✅ SQLite 内置，**零新增依赖**；与 MemoryItem **同库**，事务一致天然
- ✅ 查询走倒排索引，无需每次全量分词
- ❌ **2 字中文查询失效**（trigram 最少 3 字符）——"学习""看书"这类双字词查不到
- ❌ MATCH 语法对复杂布尔/短语支持弱

**核心权衡**：jieba BM25 强在双字词、FTS trigram 强在子串容错——二者是**互补关系，不是替代关系**。这正是"去留"问题真正的岔路口。

## 三、四个选项详析

### 选项 A：保留现状（不接线）
- **成本**：零。
- **收益**：零。死代码继续死着，`init_db` 每启动建一张永不写入的表，`test_p0` 测着一个生产不用的功能。
- **风险**：**误导**——下一位维护者看到 FTS 表+测试，会以为系统有全文检索能力。这是所有死代码的共同毒害。
- **判定**：❌ 不可取。维持现状是唯一"免费但有害"的选项。

### 选项 B：移除（删 fts.py + init 调用 + 相关测试）
- **改动**：删 `storage/fts.py`；`db.py:7,16` 删 init_fts；`test_p0.py` 删 TestFTS5 4 个测试（保留 Chronos）。
- **收益**：死代码清零，`.scratch`/文档同步清理，维护心智负担-1。
- **代价**：永久放弃 trigram 子串检索能力——未来若想要（中文错字是真实场景），需重写。
- **判定**：✅ 可选。适合"近期不打算动检索链路、只想消债"的保守路线。**但**：v0.3.2 刚把 schema 修对、测试写绿，此刻移除等于把刚补齐的资产扔掉——"沉没成本"反着用。

### 选项 C：接入为**并列补充**召回源（推荐）
BM25 保留（词级），FTS trigram 追加（子串级），两者**取并集**后融合打分：

```
score = 0.6 * 向量相似度 + 0.25 * BM25_norm + 0.05 * FTS_hit + 0.1 * 衰减
        （语义层）            （词级关键词）     （子串命中）   （时效）
```

- **改动**（接入点全部摸清，集中可控）：
  1. `promoter.py` 4 处同步：apply_proposal add 分支（创建后 `index_fts`）、update 分支（更新内容）、rollback（还原）、delete_memory（删索引）——注意同库同事务，`apply_proposal` 的 `s.commit()` 前用 `engine.raw_connection()` 或复用同一连接保证原子
  2. `hybrid.py`：检索时对候选 `search_fts` 取命中集合，加权进打分；对候选外的 FTS 命中可**追加召回**（补 BM25 漏掉的子串相关记忆）
  3. `tests`：test_p0 的 4 个测试直接复用；新增 1 个"写入→检索含 FTS 命中"的集成断言
- **收益**：中文检索鲁棒性实打实提升（错字/子串），测试资产变现，FTS 不再是死代码
- **风险**：① 双索引一致性要靠 4 个写入点纪律——但**同库 + 事务**内可原子，风险可控；② 打分权重需校准（0.05 偏保守，先小后调）
- **注意**：BM25 每次全量重建的 M4 性能问题**不随接入自动消失**——需另做语料缓存（或用 FTS 命中率观察后决定 BM25 去留）

### 选项 D：接入为**替代** BM25
- **改动**：同 C 的写入点；`hybrid.py` 删 BM25 段，关键词层全走 FTS。
- **收益**：M4 的 BM25 重建问题一并消失；代码更简。
- **风险**：**2 字中文查询退化**（"学习""看书""开会"是记忆系统最高频查询形态之一）——这是不可接受的退化。
- **判定**：❌ 除非未来给 FTS 加 jieba 预处理 tokenizer（自定义 tokenize 模块），否则不选。**这个风险点也是 C 优于 D 的根本原因。**

## 四、权衡矩阵

| 维度 | A 保留 | B 移除 | C 并列接入 | D 替代接入 |
|------|--------|--------|-----------|-----------|
| 死代码消除 | ❌ | ✅ | ✅ | ✅ |
| 中文子串/错字检索 | — | 永久放弃 | ✅ 获得 | ✅ 获得 |
| 双字词检索 | — | 保留(BM25) | ✅ 保留 | ❌ 退化 |
| M4 BM25 性能 | 保留 | 保留 | 保留(另修) | ✅ 一并解决 |
| 新增依赖 | 无 | 无 | 无 | 无 |
| 改动面 | 无 | 小(3 文件) | 中(4 文件+测试) | 中 |
| 实现风险 | 低 | 低 | 中(双索引一致性) | 中 |
| 维护心智 | 最差(误导) | 好 | 好 | 好 |

## 五、推荐

**推荐 C：接入为并列补充召回源**，理由按权重排序：

1. **价值真实**：中文记忆检索里，错字/子串是高频现实（用户输入不可能永远精准），trigram 是 SQLite 白送的能力，不接可惜
2. **成本可控**：写入点已确认只有 promoter.py 4 处，同库事务可保原子；测试已就绪
3. **不牺牲现有能力**：BM25 保留，双字词不退化（这是否决 D 的同一把尺子）
4. **时机建议**：**决策现在定（记入 ADR-0008），实施排在 v0.3.3 P1 安全项之后**——先堵安全口子（SSRF/备份/MCP），再接功能。安全是必修，FTS 是选修。

**备选**：若大哥判断近期不会碰检索链路、想先消债，选 B（移除）也可行——但小弟会心疼那 4 个刚写绿的测试和修对的 schema。

## 六、留给 ADR-0008 的三个决策问题

1. 关键词层走**并列（C）**还是**移除（B）**？
2. 若走 C：FTS 命中对打分的权重起点取 0.05，是否接受"先保守后校准"？
3. FTS 的索引同步策略：**同事务内同步写**（强一致，推荐）还是**异步 worker 补写**（弱一致，多一个失败点，不推荐）？
