# 提示词：为 Remembrance-System 深化「论文可信度体系」设计

> 用法：将下方【提示词正文】整段复制给 GPT-5.6 Sol。其输出的完整方案将交由 DeepSeek-V4-Flash 执行实现。

---

## 提示词正文

```text
# 角色

你是一位深耕 AI Agent 长期记忆系统与证据工程（evidence engineering）领域的资深架构师。你深刻理解学术论文的可信度分层问题（证据真实 / 结论可靠 / 结论适用）、复现性危机、以及"论文结论必须经过本地验证才能成为系统参数处方"这一工程原则。你擅长把抽象的可信度哲学转化为可落地的、带校验的工程机制，且不回避现实约束（如缺乏标注评估集）。

# 任务背景（已实现的系统，直接采信）

目标系统是 Remembrance-System（Python 3.11+ / FastAPI / SQLite+FTS5 / ChromaDB / jieba BM25），一个 AI Agent 长期记忆引擎，已实现"论文驱动的参数调整建议"功能（辅助模式），当前状态：

- 论文摄入：arXiv 定时拉取（默认 `cat:cs.AI`），**只有摘要**（`RawDocument.content` 为 abstract 文本），存 `source_type="paper"`
- 批量窗口触发：未处理论文 ≥5 篇 或 最老等待 ≥7 天 触发一批，单批 ≤10 篇
- LLM 建议生成：`PARAM_ADVICE_SYS`（18 条约束，Only output JSON），输出 suggest / abstain 判别联合
- 三层校验（已实现）：
  1. **证据真实**：evidence 的 quote 必须是论文内容归一化后的真实子串（防 LLM 虚构引用），source_id 必须属于本批次
  2. **结论可靠**：批量多篇对照（LLM 同时看多篇，矛盾须 abstain）+ 置信度阈值 0.85 + abstain 优先（宁缺毋滥）
  3. **结论适用**：禁止直接复制论文数值（除非证明语义/尺度等价）、单次最大变化约束（max_delta_per_apply）、收益必须表述为 hypothesis、强制输出本地验证计划（Recall@10 / MRR@10 / 零结果率 / 误合并率 / P50-P95 延迟 / 按意图分桶）
- 人工闸门：建议进入 pending 队列，`POST /param-suggestions/{id}/decision` 由人批准/拒绝；批准后带 before/after 快照应用，可追加式回滚；**绝无自动应用路径**
- 参数白名单：仅 4 个检索权重（`RETRIEVAL_W_VECTOR/BM25/FTS/DECAY`）+ 2 个去重阈值（`DEDUP_MERGE/UPDATE_THRESHOLD`），default deny，安全参数物理排除
- 关键文件：`remembrance/parameters/`（registry/schemas/validation/advisor/queue/runtime/service）、`workers/param_advice_worker.py`、`api/routes_param_advice.py`
- LLM 调用封装：`chat_json(sys, user)`（内部已 3 次重试）；提示词风格统一 "Return strict JSON ... Only output JSON"
- 测试纪律：核心函数必须有不 mock 的冒烟测试（真实最小输入直调）；mock 仅允许外部网络

# 本次任务：深化「论文可信度体系」

在既有三层校验之上，设计以下五个深化方向的**完整可实施方案**。核心命题是：**"论文可信度"不应只是入口过滤，而应让"本地验证"成为比论文本身更重的裁判。** 你需要在遵守下述硬约束的前提下，裁定每个方向怎么做，并直面"系统无标注评估集"这一现实约束。

## 方向一：论文质量信号（成本最低，先行）
arXiv API 的 `comment`（含是否被会议接收）、`journal_ref`、作者、引用关系等信号，目前摄入时全部丢弃。设计：
- 哪些信号值得采集、如何采集（arxiv.py 适配器改造）
- 如何**防止 LLM 伪造信号**（信号必须来自结构化字段而非 LLM 推断）
- 信号如何进入建议生成：作为 LLM 上下文 / 作为置信度加权 / 作为硬门槛（如非 peer-reviewed 摘要不产生建议，只参与对照）

## 方向二：本地验证闭环（shadow mode）——必须直面"无标注评估集"
系统没有 ground truth 评估集（没有人工标注的相关性判断）。请设计**最小可行验证闭环**，从以下约束出发（不得假装有标注数据）：
- 方案 A：影子进程 A/B 运行——新参数在影子进程跑一段观察期，用**隐式信号**对比（检索利用率 / 用户反馈 /feedback 的 helped 与 hallucination_risk / 零结果率 / 延迟）而非显式相关性
- 方案 B：自动构建轻量评估集——从现有记忆库自动采样查询（如从 chat lane 的历史消息取样），无标注但可做相对对比（新旧参数下同一查询集的召回差异）
- 方案 C：降级为"人工验证清单自动化"——系统生成可执行的评估脚本（跑 Recall@10 需要标注，不可行时改为统计指标），大哥运行后回填结果
- 请裁定：最小可行版本选哪个/如何组合；批准后是"立即生效 + 观察期可回滚"还是"观察期达标才生效"；观察期多长；**是否保持人工闸门不变**（本系统明确要求：最终应用仍需人工批准，验证自动化只是给人工提供证据，不得取消人工）

## 方向三：建议时效（时间维度）
论文结论会随 SOTA 迭代过期。设计：
- 建议携带论文 `published_at`；过期策略（如发布超 N 个月的建议降权 / 标记"可能已过时"）
- 与现有 `registry_version` / snapshot hash 机制如何协作（参数配置版本 vs 建议时效是两回事）
- 已应用参数（override）的"健康复查"：是否需要对长期未复查的生效参数定期重新评估

## 方向四：多篇矛盾显式化
当前矛盾处理是"LLM 自行判断后 abstain"，不可审计。设计：
- 是否让 LLM 显式输出 `contradictions`（如发现矛盾的证据对）供人审阅
- 矛盾时策略：整批 abstain / 仅保留一致子集 / 生成"矛盾报告"进队列由人裁

## 方向五：验证结果回流
批准后的人工/自动验证结果（如回填的 Recall 数字）如何回流系统：
- 新表设计（建议维度的评估记录）
- 回流后如何影响未来建议（如某类论文反复验证失败 → 该类信号降权）

# 硬性约束（不得违背）

1. **宁 miss 不脏写**：宁可 abstain 也不产出弱建议；所有校验失败即丢弃，不自动修正
2. **人工闸门不变**：无论验证自动化到什么程度，参数最终应用必须经人工批准；验证只提供证据
3. **证据真实校验加强**：任何新增的"信号"（质量信号、验证结果）必须来自可信来源（结构化字段 / 系统测量），不得由 LLM 生成后直接采信
4. **测试纪律**：每个新核心函数必须有不 mock 的冒烟测试
5. **门面铁律**：不移动现有实现、不改旧 import 语义，只增量新增
6. **风格一致**：提示词延续 PARAM_ADVICE_SYS 的 JSON 约束风格；表结构沿用 SQLModel + Column(JSON)；路由薄、逻辑下沉 service
7. 零硬编码：新阈值一律进 settings 或注册表声明
8. 中文注释，代码/标识符英文

# 输出要求

输出可直接交给执行者逐条实施的中文完整方案，含以下章节（每个决策附理由）：

1. **可信度体系总览**：五个方向如何融入现有三层过滤，演进后的完整数据流（含验证闭环与回流的生命周期）
2. **论文质量信号设计**：字段清单、采集方式、防伪造校验、进入建议的方式（上下文/加权/门槛）及对现有 `schemas.py`/`advisor.py` 的具体改动点
3. **验证闭环设计**：裁定后的最小可行方案细节——数据流、观察期参数、隐式信号定义、评估记录表设计（SQLModel 风格）、与人工闸门的关系；若选了影子进程方案，说明进程形态（独立进程/线程/复用 scheduler）与隔离方式
4. **建议时效设计**：published_at 采集、过期策略参数、与 registry_version 协作、生效参数复查机制
5. **矛盾显式化设计**：LLM 输出 Schema 变更（含 JSON 示例）、策略裁定
6. **验证回流设计**：评估表结构、回流对建议生成的影响机制
7. **文件改动清单**：新增/修改文件与关键函数签名（基于现有 `remembrance/parameters/` 结构）
8. **实施顺序**：分步骤、每步可独立验证（建议方向一先行，因成本最低）
9. **测试计划**：冒烟测试用例清单（不 mock）
10. **风险与对策**
11. **决策结论汇总**：五个方向各自的裁定 + 理由；特别回答：**"本地验证 > 论文可信度"这一命题是否成立？成立的话边界在哪（哪些场景下论文本身仍是主要依据）？**

# 约束

- **不要向我提问**。信息不足处做合理假设，显式标注【假设】。
- 输出中文；代码/字段名英文。
- 与现有实现冲突时显式说明冲突点与取舍。
- 方案具体到可直接照做，避免"建议考虑""可引入"类模糊措辞。
```

## 使用流程

1. 复制上方【提示词正文】整段 → 发给 GPT-5.6 Sol
2. GPT 输出 → 原样复制回来发给小弟（DeepSeek-V4-Flash）
3. 小弟按方案逐条实施，测试全绿后交付

## 备注

- 提示词已内置既有实现全部事实（三层校验 / 人工闸门 / 白名单 / 测试纪律），GPT 无需看仓库
- 五个方向均带"待裁定"标记，重点是**方向二**：已明确告诉 GPT 系统无标注评估集，防止它设计出空中楼阁
- 硬约束第 2 条锁死"人工闸门不变"——即便 GPT 想把验证闭环做成全自动，也会被这条拦回来
