# 工程术语对照表（给维护者的大白话版）

**这份文件是干什么的**：Agent 交活时会说「契约」「冒烟」「门禁」「fallback」这些行话。这份表把它们翻成大白话。
**它不干什么**：不解释兰台自己的概念（沉潜、拾遗、樊篱…）——那些在 [`CONTEXT.md`](../CONTEXT.md) 词汇表里，含出处和传说。

> **用法**：Agent 汇报里出现看不懂的词，`Ctrl+F` 在这页搜。搜不到就把词抄进对话框问一句——那说明这份表该补了。

## 〇、先看这个：怎么读一份 Agent 汇报

Agent 的汇报有固定套路。看懂这个骨架，八成内容你就不用逐字读了：

| 汇报里的板块 | 它其实在回答 |
|---|---|
| **交付** / **新增** | 我**改了哪些文件**（列给你对账用，看不懂文件名没关系） |
| **实测** / **门禁** | 我**自己跑过什么、结果如何**（这是最该看的部分） |
| **发现的缺陷** | 干活路上**顺手修的真问题**（通常是好消息） |
| **未做 / 守住的人工闸门** | **故意没碰的地方**，等你决定 |
| **已知不一致（如实登记）** | 我**发现了但没改**的事，以及为什么——不是漏了，是刻意留着 |

**三句话抓住要点**：①东西做完了吗？②测试真跑过吗（看「实测」里有没有具体数字和「passed」）？③有没有要我做决定的？

**看到「✓ 已完成」要留个心眼**：这类勾选是 Agent 自己打的。可信度取决于它**旁边有没有可核对的证据**（提交号、测试通过数、命令输出）。没有证据的勾选，值得追问一句「怎么证明的」。

## 一、这是一段代码在干什么

拆开看，一个改动就是四件事：

| 行话 | 大白话 | 为什么重要 |
|---|---|---|
| **契约（contract）** | 一份**不许单方面改**的约定。比如「你给我这个格式的数据，我一定还你这个格式的结果」。改契约=会让所有调用方出事，所以必须留痕、走审批 | Agent 常说「对外行为逐字节不变」就是在保证没动契约 |
| **接口 / 签名（signature）** | 函数的**门牌号**：它叫什么名字、要收哪几个参数、还回什么 | 门牌号不变 = 里面的装修随便改，外面住户不受影响 |
| **实现（implementation）** | 门牌号背后的**具体做法** | 「改实现不改契约」是安全重构；反过来就是危险动作 |
| **Schema（表结构）** | 数据库里的**表格有几列、每列装什么**。改它要动老数据 | 「schema 变更」+「迁移」通常意味着这活得单独立项，不能塞进现有活里 |

**常见评价词**：

| 行话 | 大白话 |
|---|---|
| **幂等（idempotent）** | **重复做一遍结果不变**。像电梯按钮按三下和按一下效果一样。配置脚本、补数据都该幂等 |
| **降级（degrade / fallback）** | **主路走不通就走备路**。查不到就返回空，甭把整个对话拖垮 |
| **静默降级** | 出错了**不闹**，悄悄走备路、记个日志了事。对钩子（hook）来说这是要求，不是偷懒 |
| **硬失败 / 报错退出** | 反过来：**宁可停下也不糊弄**。安全相关的事该这样（比如配置填错了就不许启动） |
| **断言（assert）** | 代码里的**「我保证这里一定是这样」**。不成立就当场炸，好过悄悄错下去 |
| **硬编码（hardcode）** | 把值**写死在代码里**而不是做成配置。项目纪律一般禁止（密钥、路径、阈值都不许写死） |
| **归一化（normalize）** | 把五花八门的输入**收拾成同一种标准格式**。A 宿主叫 `prompt`、B 宿主叫 `message`，归一化后都叫 `query` |
| **抽层 / 抽成模块（extract）** | 把**能独立的一块搬出去单独放**，好复用、好单独测 |
| **纯函数（pure function）** | **只靠输入算输出**、不碰外界（不读写文件、不联网）的函数。最好测，因为没有副作用 |
| **副作用（side effect）** | 函数**对外界的改动**：写库、发网络请求、改文件。测试时最麻烦的就是它 |
| **边界（boundary）** | 系统与外部世界的**接缝处**。出了这个边界的东西就不归你管了（用户输入、外部 API） |

## 二、这些东西是怎么被验证的（测试行话）

**核心一句**：一个测试的价值 = 它**会不会真的报警**。看着很绿但从来不报警的测试，等于没有。

| 行话 | 大白话 | 陷阱 |
|---|---|---|
| **测试（test）** | 一段**自动检查**代码：给定输入，看输出对不对 | — |
| **单测（unit test）** | 只测**一小块**（一个函数），不牵扯整个系统 | — |
| **集成测试（integration）** | 测**几块拼一起**能不能配合 | — |
| **端到端 / E2E** | **从头发到尾**全流程走一遍，像真人用一样。最可信，也最慢 | E2E 常能揪出单测揪不到的 bug |
| **冒烟测试（smoke test）** | 最基本的**「通不通电」**检查：真实输入跑一遍，只确认**不炸**、主路能走通 | 项目铁律：**每个核心函数至少一个冒烟测试**（见 AGENTS.md） |
| **不 mock 的冒烟** | 测试时**不许假装**，内部逻辑必须真跑 | mock 只能用在外部网络（大模型/嵌入）这类真跑不了的依赖上 |
| **mock（打桩 / 替身）** | **假装**某个东西，好让测试跑起来。假装 llm 返回一句固定话 | **规矩**：不许用 mock 让被测函数「跳过」它自己的计算——那就变成演戏给自己看了 |
| **替身 / stub** | 和 mock 差不多，通常指**站在真位置上的假货**（比如假嵌入服务） | 兰台要求：用的替身**必须写明**、且只能用在外部网络面 |
| **回归（regression）** | 「以前是好的，现在坏了」——**新改动把老功能弄坏了** | 「零回归」= 老测试全还绿着 |
| **全量门禁** | **所有测试跑一遍全绿**，才算能交。兰台现在是 1200+ 个测试 | 汇报里若只有局部测试数，要问全量跑没跑 |
| **变异测试（mutation test）** | **故意把代码改坏**，看测试会不会报警 | 不报警 = 你的测试是摆设。这是检验「测试有没有用」的手段 |
| **红 / 绿（red / green）** | 红 = 测试失败；绿 = 通过。TDD 是**先写一个红的测试**，再写代码把它变绿 | 先红后绿，才能证明测试真的在测东西 |
| **TDD（测试驱动开发）** | 上一条的整套做法 | — |
| **断言数（assertions）** | 一个测试里检查了几个点 | 「断言零改动通过」= 老检查点一个没动还全过 |

## 三、一次改动是怎么被管理的（流程行话）

这些词是**项目自己定的规矩**，写在 `AGENTS.md` 和 `docs/development-workflow.md` 里。

| 行话 | 大白话 |
|---|---|
| **ADR**（架构决策记录） | `docs/adr/` 下的**决策存档**，一篇讲一件事：当时为什么这么定。**只记当时，不追溯改写**——像会议纪要，不回头改 |
| **票据 / issue** | 一件事的**工单**，存在 `.scratch/<功能名>/issues/` 下。一票一件事，可独立验收 |
| **规格 / spec** | 干活前写的**设计说明**：要做什么、不做么、验收标准是什么 |
| **分诊标签（triage label）** | 给票据贴的状态：`needs-triage`（待你看）/ `needs-info`（缺信息）/ `ready-for-agent`（我能独立干）/ `ready-for-human`（**得你拍板**）/ `wontfix`（不干） |
| **垂直切片** | 一个切片 = **一小块能单独完工、单独验收的完整功能**。禁止「先建所有表、再写所有接口」这种一次性铺开的拆法 |
| **门禁（gate）** | **过关检查**。测试全绿 + 质量指标达标，才准往下走。兰台的门禁命令见 `development-workflow.md` 阶段 5 |
| **人工闸门（human gate）** | **必须你来按的按钮**。兰台最硬的一条：`git push`（把代码传到网上）和打版本标签，**Agent 只能准备、不能代按**——见 `docs/development-workflow.md:106` |
| **收口 / 收尾** | 一票活**干完并归档**：改的改完、测的通过、文档更新、票据上记一笔 |
| **留痕** | 把**过程和证据记下来**（决策为什么这么定、测试怎么跑的），将来好追溯 |
| **宁 miss 不脏写** | 兰台的核心数据纪律：**拿不准就什么都不做**，绝不瞎猜着改。所以很多地方宁可返回空、宁可进待审队列 |
| **待审队列（pending_review）** | 不确定的东西**不丢、也不自动采信**，先存起来交给你/特权 Agent 裁决 |
| **refactor（重构）** | **只改内部结构，不改对外行为**。像把房间重摆一遍，水管电路没动 |
| **commit（提交）** | 把一批改动**打包存档**，带一句说明。汇报里的 `2f4b84d3` 就是提交号 |
| **push（推送）** | 把提交**传到远端**（GitHub）。**兰台里这是你的活**，Agent 不碰 |
| **tag（版本标签）** | 给某个提交起个**版本号名字**，比如 `v0.21.0`。也是你的活 |

## 四、看到这些数字，怎么判断好还是坏

Agent 的汇报里常出现数字，认准这几个就够：

| 你看到的 | 它的意思 | 什么算好 |
|---|---|---|
| `1220 passed / 0 failed` | 跑了 1220 个测试，全过、零失败 | **`0 failed` 是硬杠**。有 failed 就没资格交付 |
| `7 passed`（某个文件） | 只跑了那一小块 | 局部证据，不能替代全量门禁 |
| `ruff` 全过 | **代码风格检查**过了（格式统一、没明显低级问题） | 过了是应该的；没过要问 |
| `PASS`（遗忘质量） | 质量指标达标 | 兰台有专门的记忆质量检查，也是门禁之一 |
| `+1405 / −39` | 这次改动**加了 1405 行、删了 39 行** | 数字大小本身不代表好坏，只是规模 |

**判断一句话原则**：**有没有 `0 failed`**，**有没有具体命令和输出**。这两样齐了，这次交付基本可信；缺了，就该问。

## 五、看不懂时，照着问这三句

不需要你懂技术，问这三句就能把任何一段行话逼出人话：

1. **「这个改动，对我实际使用有什么影响？」** —— 逼他把技术名词翻译成后果。
2. **「你怎么证明它真的能跑？」** —— 逼他给证据（测试输出、命令、提交号），而不是给勾选。
3. **「这里有没有需要我做决定的地方？」** —— 逼他说出人工闸门在哪，而不是替你决定了。

> 第 2 句尤其重要。项目的测试纪律（见 `AGENTS.md`）就是为了让这个问题**总能被回答**——如果答不上来，那是交付没做完，不是你不懂。
