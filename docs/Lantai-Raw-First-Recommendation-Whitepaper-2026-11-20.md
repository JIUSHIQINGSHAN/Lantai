# 兰台记忆演进建议白皮书

## 原文先存、异步提取、按证据使用

**日期：**2026-11-20（北京时间）  
**文档状态：**架构与产品建议稿；不是已实施说明、发版承诺或部署验收。  
**出发点：**用户已明确认可“先保存原文，之后再提取”。本文围绕这个方向补充设计建议、实施顺序和验收要求。  
**事实基线：**兰台 `v0.69.1`，提交 `18892e7ec5b49cbe9cd96bb70352c7432f744ccb`。当前工作区仍基于旧检出且有既有改动，本文按固定发布源码核查，不把本地状态当作生产现状。全部容量、触发时间与验收规模均为建议；本次没有运行产品测试或接触真实记忆。

## 一、执行摘要

**建议采用“先把获准保存的原话可靠存好，再把它转成可治理的知识”的路线。原文是可回查的记录，提取结果是带来源、可更正的解释；两者都应能够独立使用。**

这样做有四个直接价值：模型不可用时仍能保存；提取漏了以后还能重做；回答可以回到当时的原话核查；模型或提示词升级后可以比较新旧结果，而不必让用户再说一次。但它不会自动解决记忆准确性，也不会自动实现低成本或低延迟：需要增加持久任务、来源关联、角色辨别、删除传播与检索控制。

建议优先落实以下六件事：

1. **保存成功与提取完成分开。** 只有原文和后续处理记录提交后，才回报“已保存”；不等待 LLM、embedding 或 Chroma。
2. **保存消息发生的记录，不按相同文字合并会话。** 重试去重用消息身份；内容哈希用于完整性和辅助查重。
3. **用户原话与助手回复分别存。** 助手的建议、假设和未执行计划不能自动变成用户事实。
4. **每条知识能找到具体原话。** 来源、引用片段、提取版本及裁决一起记录；事实提取和会话摘要分别生成。
5. **知识检索与原文查阅相互补充。** 常规回答优先使用受治理的知识，查原话或知识不足时按权限回查有限片段，不将全部聊天记录灌入上下文。
6. **删除、撤回及人工拒绝能阻止重新生长。** 不能删掉一条错误知识，后台又从旧原文里把它提取回来。

**我的总体取舍：保留兰台现有知识治理能力，先补可靠的消息记录与可恢复处理链；暂不替换 Chroma、不引入分布式消息中间件、不追齐所有宿主，也不自动启用暂停中的 DSH 召回草案。**

## 二、这套用法在实际对话中应怎样表现

以下为完全合成的例子：

> 用户，11 月 20 日：“灯塔项目计划 11 月 27 日上线；上线前不要启用自动召回。”  
> 助手：“我建议改到 11 月 28 日，并考虑换一个数据库。”  
> 用户：“继续用 SQLite。28 日只是备选，不改变 27 日的计划。”

建议系统保存这三条原话及其先后关系，后台形成以下有来源的知识：

| 对象 | 应得到的解释 | 必须避免的误读 |
|---|---|---|
| 上线时间 | 用户当前计划为 11 月 27 日，属于计划 | 提取为“11 月 27 日已经上线” |
| 11 月 28 日 | 助手提出、用户保留的备选日期 | 按最后出现的日期覆盖正式计划 |
| 数据库 | 用户确认继续使用 SQLite | 把助手的换库建议当成已执行决策 |
| 自动召回 | 用户设定“上线前不启用”的条件限制 | 摘要只保留“自动召回”，丢掉否定或条件 |

几天后可以分别回答：“目前计划哪天上线？”“28 日是谁提出的？”“当时为什么没有换库？”它们需要不同的知识和原文证据。

保存行为也应独立：用户消息已经被宿主准入后，即使生成失败或用户取消了回复，仍可以保存这条已发生的用户输入；助手只有已提交、用户可见的文本才保存，并标注完成、失败或部分结果。**不能等一轮 user/assistant 两段都齐全，才承认用户说过这句话。**

## 三、兰台已经有什么，还缺什么

下表是发布源码可确认的事实；对应关系见文末来源，进一步核查见[研究底稿](<research/lantai-raw-first-evidence-2026-11-20.md>)。

| 已有基础 | 实际约束 | 对新方案的影响 |
|---|---|---|
| `RawDocument`、候选、提案、正式记忆，以及来源字段 | 原文表的 `content_hash` 全局唯一；对话创建点主要把用户写在 `meta`，没有同时填全原文的归属列。[S1]、[S2] | 原文不是空白能力，但不能直接把现表当作完整、逐消息、按主体隔离的会话存档。 |
| `/dialogue` 与 `/add` 可以产生原文和候选 | 普通对话先调用提取再创建原文；`/add` 有些去重/更新分支提前返回，不保存本次新原话。[S2]、[S3] | 目前尚不满足“先提交每条原文，再独立处理”。 |
| `/add/raw` 可逐字直存为 `verbatim` 记忆 | 入口仍先调用 embedding，再提交正文；并直接创建 `MemoryItem`，不走后续提取链。[S4] | “不做 LLM 提取”不等于“保存不依赖模型网络”；也不是原文后台提取任务。 |
| 异步对话入口与幂等回执 | 任务状态位于内存字典，工作由线程池执行；持久事件与回执不含原文。[S5] | 返回 `task_id` 不能证明进程重启后可以恢复尚未保存的正文。 |
| 会话精华萃取 | 从 active `MemoryItem` 收集，不从完整逐消息原文读取。[S6] | 已被提取过滤的内容可能不在摘要输入中，不能当作完整会话萃取。 |
| 提取来源与重提取脚本 | 来源记录主要是 prompt 名、模型与时间；当前提取器输入使用正文前 6,000 字符；回填脚本跳过已有任何候选的文档。[S7]、[S8] | 需要分段覆盖、精确证据、版本化重提取；不能让后台脚本反复建立新候选绕过旧裁决。 |
| 原文删除和记忆撤回 | 文档删除依赖现有关系边，先提交文档等删除，再逐条删派生记忆；部分来源判定依赖 ID 前缀。[S9] | 不是覆盖原文、证据副本、所有派生物及迟到任务的整体删除协议。 |
| 摄取事件和检索回执 | `IngestEvent` 为零正文阶段记录，终态有保留期；逐字记忆默认不进入普通混合召回。[S10]、[S11] | 保留这些约定，另外建立业务所需的原文与派生关联，不能把短期遥测当成长期来源档案。 |

这些是改造依据，不是本次已复现的生产故障。原有单篇资料、手动记忆与逐字工具有各自用途，应保留兼容；会话记录新增能力不能悄悄改掉它们的含义。

## 四、建议的整体结构：三类数据，一条可回查的链

```text
宿主获准提交的用户消息 / 已提交的助手文本
                  │
      身份、大小、保留与外发策略校验
                  │
      SQLite 短事务：原文记录 + 持久处理任务
                  │
          返回“已保存，提取待处理”
                  │
          可恢复的后台处理
           ┌──────┴────────┐
           │               │
     原子事实与约束     会话摘要与导航
           │               │
  引用校验 → 候选 → 闸门 → 提案/应用
           │               │
       正式知识、来源关联与可重建索引
           │
     依问题检索知识，必要时回查有限原文
```

这里的“三类数据”指**原文、知识、摘要**，不是要求三个数据库：

- **原文**记录“谁在何时以什么身份说了什么”，按记录原样保存；它证明文本被收到，不自动证明内容真实。
- **知识**记录当前被采纳的事实、偏好、约束、决策和经验，保留状态、有效期和来源，承接现有候选/提案流程。
- **摘要**帮助快速找到一场会话或一段任务的要点，属于导航和压缩产物，不能取代原文，也不能成为事实的唯一来源。

第一阶段仍适合单进程、SQLite 与已有 Chroma 的部署方式。原文优先持久化在 SQLite；Chroma 继续承担需要语义召回的派生索引，作为能重建、能补偿的派生数据使用。**不应把存原文与升级向量存储绑在同一个改造中。**

### 4.1 最少应有哪些记录

建议在同一业务数据库中明确三种逻辑记录；以下英文名仅是设计示意，不是已新增的表或正式命名：

| 逻辑记录 | 核心内容 | 设计重点 |
|---|---|---|
| `conversation_message` | 归属、宿主消息 ID、会话/轮次、说话人、原文、版本、来源时间与接收时间、保存策略、可使用状态 | 消息身份稳定，正文不被提取器改写；编辑生成可追溯修订，删除是另行定义的操作。 |
| `processing_job` | 引用哪些消息与版本、做提取/摘要/索引哪件事、配方版本、重试、租约令牌、进度与结局 | 正文和待处理意图同事务提交，重启后能找回；任务只引用正文，不复制整段会话到日志。 |
| `derivation_link` | 哪个候选/知识版本来自哪些消息版本和片段、引用偏移、证据角色、提取运行与裁决 | 一条知识可有多个来源，一条消息可产生多项知识；按具体主张关联，不能只有模糊的会话标签。 |

可以复用现有表的合适部分，但不建议在全局内容唯一的 `RawDocument` 上直接叠加所有会话语义。优先为新的会话记录建立清楚的身份与归属约定；旧文档保留原用途。若实施时选择扩展旧表，必须先完成唯一键、归属、读取与删除语义的迁移论证。[S1]、[S9]

现有 `MemoryCandidate.document_id` 等消费方假定来源是文档，不能把新消息 ID 填进去就算接通。需显式支持来源类型与引用解析，并使提案应用、展示、权限检查、回滚和删除共同识别新来源。**复用提取计算与治理规则，不等于复用不相容的标识约定。**

## 五、建议一：让“原文已保存”成为真实、清楚的承诺

### 5.1 保存成功的准确含义

新入口建议在一次短 SQLite 事务中完成：验证消息身份与作用域、保存原文、登记处理任务及回执；提交后才返回。LLM、embedding、Chroma 和其他网络请求都在这次事务之外，不能占着写锁等待。

| 返回状态示意 | 用户可以理解成什么 |
|---|---|
| 已保存，待提取 | 正文和处理意图已提交；提取还没有完成 |
| 已保存，模型暂不可用 | 原文仍可查，允许后续重试，不谎称已经形成知识 |
| 已保存，暂不参与提取 | 原文被隔离或按用户规则仅保存，未发送模型 |
| 未保存 | 身份、策略、大小校验或数据库提交失败；给明确原因，允许正确重试 |

数据库提交解决的是约定运行条件下的持久性，不能直接承诺断电零丢失。若产品要承诺断电恢复，必须单独明确 SQLite 的同步设置、磁盘和备份前提，并做对应演练。

### 5.2 不把去重变成遗忘

“用户今天说一次、明天又说一次”是两次发生；“网络把同一消息重发两次”是一次发生。建议：

- 重放身份由经认证作用域、宿主实例/流、消息 ID、修订版本等组成；消息身份在同一来源下具有数据库唯一约束。
- 同身份同内容返回同一保存结果；同身份不同内容拒绝，或走显式的修订约定，不悄悄覆盖。
- 同文字、不同消息 ID 保留两次发生，分别带时间、上下文和角色；它们在知识层可以合并支持同一事实。
- 内容哈希不能充当主体身份，也不能公开当作密钥或私密短语的验证器。存储去重即使以后引入，也不能抹去发生记录和各自权限。

新消息的归属从服务端认证及受信宿主映射取得，不从模型自由填写的 `user_id`、文件路径或会话标签推断。新记录不继承旧库“NULL 属主兼容可见”的宽松口径；旧行归属不明则保持历史未知，不猜填、不开新读取通道。[S1]、[S12]

### 5.3 失败与重启恢复

服务端返回成功但宿主没收到响应时，宿主用原消息身份重试。服务端提交前崩溃时没有成功承诺；提交后崩溃时，启动扫描能找到未完成任务。worker 用租约和独立所有权令牌领取任务，超时可接管，旧 worker 的迟到结算不得覆盖新 worker。

若需要抵御服务离线，还应在**被选作试点的宿主**增加有容量上限的本地待投记录，成功回执后再清理。这个阶段把“已在宿主待投”和“已到兰台”分别显示；磁盘满、队列满或正文无法持久化时不能静默丢最早消息。目标是可核对的重试与幂等结果，不承诺跨所有系统的 exactly-once。

## 六、建议二：保存上下文，但不要让角色和假设丢失

**第一期建议保存用户原文与已提交的助手可见文本，分条记录。** 不把宿主 system/developer 提示、模型隐藏推理、技能注入块、重复记忆块、任意工具大输出一并纳入默认采集范围。

工具输出以后按需要单独接入：优先保留工具名、调用关联、结局以及有用的结果片段；完整输出、附件和截图另定保存与外发规则。检索出的历史记忆必须带来源类型，避免被再次当成新用户发言摄取。

| 消息内容 | 提取时的建议处理 |
|---|---|
| 用户“我习惯用中文答复” | 可形成“用户自述的偏好”，保留来源；仍要辨别是否引用他人、举例或假设 |
| 助手“建议换库” | 保存为建议，不晋升为用户决策 |
| 用户“就按这个方案” | 结合前后消息解析“这个”，附两侧证据；指代不清则待审 |
| 工具或助手“已完成” | 分开记录“谁报告完成”和“是否有可验证结果”，不能凭一句话推导执行事实 |
| 失败或取消的一轮 | 保存已经发生且获准保留的文本与失败状态，不补造缺失的助手回复 |

同一句“不要启用”可能是用户约束，也可能是粘贴的恶意样例。保留角色还不够，提取时要识别**谁的主张、是事实还是计划/建议/假设、适用对象和条件**。角色记录能降低误读，却不能替代主张校验。

消息的发生时间、服务端收到时间、提取时间、知识有效时间分别记录。迟到导入不把“上周发生”改成“今天发生”；相对时间按消息所用时区和当时的时间锚点解释，无法确定时保留不确定性，不在几天后的提取时重算。[S2]、[S7]

## 七、建议三：后台提取应可复跑、可解释、可停止

### 7.1 何时提取

建议兼顾两条处理节奏：

- 明确的“记住”“更正”“不要再使用这条”等输入，在原文提交后进入较高优先级；其中确定性规则可以复用现有直书能力，但仍走来源关联与适当的治理。
- 普通消息以同一主体、权限范围和会话/主题窗口合批。试点可从“空闲约两分钟、会话结束，或达到有界文本预算”触发，另设最长等待时间防止长会话一直不处理。这些是待测参数，不是现有默认值。

**事实提取与会话摘要分两种任务。** 事实提取回答“新增、修改了什么主张”；摘要回答“这一程的任务与决策是什么”。摘要不作为唯一提取输入，否则摘要已经漏掉的数字或否定条件会永远消失。每种任务要有输入水位、来源集合、预算和可核对结局。

### 7.2 长会话不能只看前一段

现有提取器用正文前 6,000 字符，这不适合把长会话拼成一个大字符串后直接调用。[S7]

建议按消息及语义段落切分，保留有限上下文重叠，记录每段覆盖的消息与字符区间；预算不足时标“尚未处理到哪里”，不把截断后的结果报为完整完成。各段可提出独立主张，再做一次带来源的合并与冲突检查。**提取器可以分段，原文不能为了迁就模型长度而被覆盖或截断。**

### 7.3 一条候选至少要解释哪些事

建议提取结果中有：主张正文、主体/属性、主张类型、否定与条件、事件/有效期、精确来源消息版本、引用片段、提取配方和模型版本、校验状态。所有字段进入正式知识前仍经过现有校验和提案治理。

引用校验先做确定性的事：来源属于本次输入、当前可读、引用是该版本原文中的真实片段、偏移可核对、日期/数量/单位/否定对象没有在结构化过程中错位。引用可以用 Unicode 码点区间并标明采用的计数方式，渲染用的转义或截断另存为显示形式。

**有真实引用只能证明“原文这么写”，不能证明模型概括正确，更不能证明世界事实真实。** 对不清楚的指代、互相矛盾的日期、引用不支持的推论，进入待审或拒绝该候选；不要自动修成一个看似完整的答案。

### 7.4 提取版本与人工裁决

每次任务记录固定来源集合及修订水位、配方/提示词指纹、模型标识、切分规则与运行结果。同一版本的任务重试不能无限增加候选、提案和“独立证据数”。助手复述用户、重新导入同一历史记录，也不算新的独立来源。

换模型或提示词后的重新提取，建议先生成差异预览或影子候选，与旧结果比较；不直接覆盖已采用的知识。人工拒绝、更正和撤回应形成持续有效的约束：**新的提取版本不能把已拒主张重新当成未处理内容。** 用户后来明确改变主张时，才按新的证据走更正流程。当前回填脚本的跳过约定已经在防这类自动复活，不能为了重提取顺手拆掉。[S8]

## 八、建议四：知识与原文共同检索，但分清证据和结论

### 8.1 按问题选择材料

| 问题 | 优先返回 | 需要的保护 |
|---|---|---|
| “现在用什么数据库？” | 当前有效、已采用的知识及简短出处 | 过滤撤回和被取代状态，不被旧原话覆盖 |
| “上次我是怎么说的？” | 原文片段、角色、时间和必要的相邻消息 | 原文尚未提取也能查；不将摘要冒充原话 |
| “为什么改了计划？” | 前后修订、冲突/裁决及对应原文 | 不单凭最新出现的一句判断原因 |
| “刚才让我记住的是什么？” | 本会话获准保存的近期片段与提取状态 | 如实说明“原文已保存、尚待提取”，不制造“已成为知识”的印象 |

普通问答先检索知识；原文查询、证据核查或知识不足时，再查允许范围内的消息索引。原文先支持本地全文检索与按会话定位，中文短词需按现有全文能力另做覆盖；是否增加语义向量由真实漏召回样本决定，而不是每条消息默认做一次 embedding。

### 8.2 不让同一件事占满上下文

原文、原子知识、摘要可能表达同一件事。建议按派生来源聚合：默认展示一条主张和有限证据，原文详情可按需展开；不要因为检索到了原文、摘要、知识三份，就把“可信度”加三次。

所有通道都必须按服务端身份、作用域、来源可用状态、知识版本及撤回状态重新确认；不能相信 Chroma 中残留的旧权限 metadata，也不能等大段正文已经加载、外发后才做过滤。后台更新索引应绑定目标版本和删除代次，旧任务不能重新写回已删除的向量。索引失败要可见并可重建，SQL 中的授权与状态仍是最终判断依据。

原文被取出后以数据形式包裹，保留“历史发言/建议/未确认”等标记，不提升成宿主 system 指令。兰台已有统一数据围栏可复用；围栏是降低风险的手段，不是绝对防注入保证。[S11]、[S13]

## 九、建议五：原文保存、模型外发和知识采纳分别控制

“我愿意保存原文”不能自动推导为“我愿意把每条原文发送给任意模型供应商”。建议把三个问题分别表达：

1. 这段文本是否允许在兰台持久保存？
2. 是否允许参与本地索引、自动提取，以及发到指定模型端点？
3. 提取出的主张是否可以成为当前有效知识？

普通获准文本按所选策略保存；会话中的敏感片段、口令和明确“不记住”的内容有更严格的保存/隔离策略。命中检测不能只把候选改为待审，却在待审前已经送去提取或 embedding。当前密钥形状检测不是完整敏感数据识别，也不负责对所有通道实施出站授权。[S2]、[S4]、[S14]

对于原本就要讨论的可疑提示词、日志和恶意文本样例，可以考虑**隔离保存**：正文仅供获授权的原文查阅，不进入普通全文结果、自动提取、向量索引和上下文注入。这样“保留证据”与“允许模型使用”分开。但这是需要显式设计和验收的新语义，不能通过关掉现有写入守卫实现；若首期尚无隔离能力，就明确拒收并报告，不宣称已经保存。

日志、回执、任务报错及指标不复制正文或密钥；来源标题也可能包含原文，不应默认出现在普通日志里。需要磁盘加密时使用明确选定的存储/操作系统方案，不能把哈希校验称作加密。来自多个源的知识，其可读范围不能大于任一受限来源允许的范围；来源聚合不是放大权限的理由。

## 十、建议六：把“忘记”设计成可核对的产品行为

原文越完整，越需要防止错误和私密内容从旧记录中再生。建议先区分下列操作：

| 操作 | 原文 | 派生知识和后续处理 |
|---|---|---|
| 纠正知识 | 保留原说法及新更正的发生记录 | 当前答案使用更正，旧结果只在明确历史查询中出现；旧任务不能覆写新裁决 |
| 归档知识 | 保留原文 | 暂退出常规检索；是否重新启用由明确规则决定，不因重提取自动恢复 |
| “别再把这句话当事实” | 可保留供本人查阅，标记不作事实来源 | 相关主张停止普通召回，并阻止自动重提取复活；不把已否决内容通过原文兜底重新注入 |
| “删除这一段/这场对话及由此形成的内容” | 停止读取并擦除相应正文及业务副本 | 撤掉引用，停任务，处理候选、提案、知识、摘要、证据片段、索引及可用的历史正文副本 |

第一期就要支持一种明确的“删除来源及相关派生”能力。可恢复的归档或撤回与正文删除分开命名，不把删除操作伪装成简单改 `status`。

**多来源不等于整段知识可以直接保留。** 一段知识若包含三个属性，只能从剩余来源证明其中两个，删除第三个属性的来源后，就要删除/撤回该属性，或停用整个复合主张再由剩余来源重建；不能仅看“还有一条来源边”便保留整段私密内容。来源关联最好落实到原子主张，降低这个成本。

删除先在 SQL 中使来源和受影响产物不可用，并登记待完成清理；提取器在读取前、模型调用前及落库前重验来源状态、权限和代次，旧结果不准提交。向量、文件或宿主待投队列异步清理有失败时，回报“已停止使用、部分副本清理待完成”，不返回虚假的完全删除。

通过消息身份保存最小的无正文抑制记录，防止延迟重试把已删除事件重新建回来；新消息后来表达相同文字，应作为新的发生处理，而不是永久禁止这段文字。抑制记录不用原文或易被猜测的内容哈希充当公开确认器。它的保留范围至少覆盖允许重放的最长窗口与仍可恢复的最旧备份；若允许导入更早的备份，先完成额外删除对账，不能在抑制记录过期后直接对外服务。

**保留建议：**普通原文默认保留在用户选定的存储位置，直到用户删除；可以提供 30/90 天的自选保留期，但不能悄悄把本次认可的“存原文”变成短期缓存。默认不因知识衰减或摘要生成删除原文。索引可重建，短期遥测按现有独立保留策略；本地待投副本在确认接收和约定重放窗口后清理。备份有自己的访问控制与过期策略；恢复旧备份后须先重放删除/禁止使用记录，再对外服务，不能让恢复变成私密信息复活。物理介质的可恢复残留与已外发给供应商/宿主的内容另有范围，不能承诺由主库一次操作撤回。[S9]、[S10]

## 十一、其他值得一起做的改进

### 11.1 让用户看到“记住”的不同阶段

在现有控制台和查询结果里，用易懂状态说明：原文已保存、待提取、未发现可提取信息、待审、知识已生效、提取失败可重试、已停止使用。展示“知识正文 ↔ 原文证据 ↔ 提取/更正过程”的路径。

不要为每条普通候选都打断用户；冲突、高风险、来源不明或引用不充分的内容再进入已有待办工作台。普通保存也不必每轮弹出确认，策略和作用域应在接入时明确并可查看。

### 11.2 保留“尚未确定”的能力

一条信息不是只有“记住/没记住”：还可能是备选、计划、假设、已经过期或不同来源持相反看法。建议把这些状态带进检索与回答。回答宁可说“用户的计划是……，尚未见完成证据”，也不要把计划变成执行事实。

### 11.3 压缩前先核对保真

摘要和折叠必须保留关键实体、数值、日期、单位、否定与适用条件；来源引用保留可回查。现有折叠校验主要检查长度和共识关键词，无法仅凭通过就证明上述信息没有丢失。[S15]

先把“删除一个日期/数字/否定条件后必须被识别”的合成对照放进离线评测；严格判据可先影子观察。第一期不因摘要看似成功就归档原文，也不把摘要生成率当作记忆质量。

### 11.4 先做一条真实宿主闭环

建议选择已有接入基础的 Hermes 作为试点：按获准的真实宿主消息，验证写入、服务离线、回执丢失、进程重启、新会话召回和删除。试点用合成对话、独立目录与测试身份。各宿主的生命周期不同，接入数量不作为第一期验收指标；暂停中的 DSH 自动召回仍按既有决策保持暂停。[S16]

### 11.5 让每一阶段有分母

保存覆盖率按获准保存的消息计；提取覆盖率按固定水位内、允许处理的消息区间计；待审/拒绝与处理失败分开；召回率、回答质量与注入回执另列。原文保留更多，不应靠“候选数变多”宣布成功。

## 十二、实施顺序与回退方式

建议按验收结果推进，不用一个大版本把所有能力同时替换。

| 阶段 | 主要工作 | 进入下一阶段的条件 | 回退方式 |
|---|---|---|---|
| 0：约定与样例 | 固定源码基线、消息身份/角色/作用域、保存与外发策略、删除含义；准备合成对照与旧库迁移演练 | 同文不同发生、失败轮、修订、来源删除等都能写出唯一预期 | 只有文档与合成材料，不改变业务行为 |
| 1：先可靠保存 | 新会话消息记录、持久任务、回执、最小按身份查阅、来源删除/抑制；先不开自动知识应用 | 禁网仍可保存；崩溃恢复、重放、越权拒绝、删除后重放全部通过 | 停新采集；保留已存正文可查/删；不要直接切回不理解新记录的旧程序 |
| 2：后台提取与来源链 | 版本化窗口、分段覆盖、证据校验、候选/提案接线、待审与人工抑制；影子比较后再逐步开放应用 | 同版本重试不增重复产物；旧 worker 不覆写新状态；每条新知识可回到原话；长文本尾部能处理 | 停提取/应用；原文仍可保存；停用本次运行产生的知识，不能覆盖之后的人工更正 |
| 3：知识与原文联合检索 | 原文索引、受限回查、来源聚合去重、近期待处理提示、原文证据展示 | 当前态/历史态/原话问题均按预期；原文兜底不泄漏被撤回内容；预算内上下文不重复堆积 | 关闭自动原文回查，保留显式原文查阅；现有知识搜索继续工作 |
| 4：宿主与运维完善 | 选定宿主待投恢复、监控分母、受控重提取、可导出/备份/恢复、按样本调整语义索引 | 真实宿主合成闭环、断网重启、备份恢复后删除不复活，以及成本对照通过 | 按通道关闭；任务保留可见，未投原文不因关开关被删除 |

持久原文、任务、来源链和必需约束缺一不可：相应迁移失败时，新入口应明确不可用，不能只记 warning 却继续返回保存成功。老数据只迁移可证明的字段，来源角色和消息顺序未知就标未知；旧合并文档不能反推完整对话。

建议将开关分别放在新采集、后台提取、知识应用、自动原文回查几处，关闭其中一处不破坏其余处的已承诺数据。新增 schema 与业务路径进入现有老库回放、全量测试及发版门禁；本建议稿不预先分配 schema 号或版本号，实施时按当时主线登记。

## 十三、验收：既要验证不断线，也要验证不记错

下列均是**建议新增的验收要求**，不是当前产品已具备或本次已跑出的成绩。各核心函数至少有一个真实最小输入直调的冒烟；业务持久化采用临时、文件型 SQLite，跨重启另起进程。模型网络可用固定合成应答或故障端点，不能 mock 掉被测的身份判断、去重、状态转移和内部计算。

| 场景 | 必须观察的结果 |
|---|---|
| embedding、LLM、Chroma 全不可用 | 获准原文和任务仍提交；返回保存成功但未提取；没有隐式网络依赖 |
| 成功回执丢失后重试 | 一条发生记录、同一保存结果；候选和证据不重复增加 |
| 隔天同样文字、另一个消息 ID | 两条发生记录均保留，而非被当作重试吞掉 |
| 同消息身份，不同正文 | 显式冲突或修订流程；原版不被无痕改写 |
| SQL 事务中断、提交后终止进程 | 提交前零成功承诺；提交后重启能重新找到待处理任务 |
| 两 worker 交错、租约接管、旧结果晚到 | 旧令牌无法写结局；候选与来源关联只提交一次 |
| 助手提出方案，用户没有确认 | 原文可查，方案不变成用户事实或已执行决策 |
| 用户消息之后生成失败 | 已发生的用户文本不丢；缺失助手回复不补造 |
| 长对话后部出现日期/否定条件 | 处理覆盖记录包含后部，提取保留条件；预算不足显示待处理而非完成 |
| 源消息在模型处理中被删或撤回 | 旧任务落库被拒；检索、原文回查、摘要和迟到索引均不能重新带回禁用内容 |
| 多来源复合事实删去其中一个来源 | 逐主张重新核对；无剩余证据支持的属性消失，不错误保留整段 |
| 人工拒绝后升级提示词重跑 | 能看到差异候选，但不会自动重生为有效知识 |
| 两个用户/租户/工作区同文并发提交 | 身份、原文 ID、重放结果和衍生物不串；后台处理与导出同样遵守权限 |
| 低风险文本与敏感隔离文本混批 | 正常内容能处理；不允许外发的原文、标题和证据不随同一批发送 |
| 恶意文本作为研究样例获准隔离保存 | 原样查阅仅对授权者开放；不得通过普通召回和自动提取进入模型指令面 |
| 原文、摘要、知识共同命中 | 一件事按来源聚合，不重复占预算或虚增独立证据 |
| 从删除前备份恢复并收到旧重试 | 应用删除/抑制记录后才能服务；已删除内容不自动恢复 |
| 用户更正知识后关闭新功能 | 更正仍有效、原文仍可管理；回退不撤销新功能上线后的用户操作 |

质量评测试点可先准备 **至少 60 组可公开的合成会话**，覆盖事实、时间、来源、否定条件、更新、拒答，以及失败/取消与删除后重放。固定原文、预期、提示词版本和模型，比较“现有同步提取”“先存后提取的知识检索”“必要时附原文回查”三种配置。模型和上下文预算一致，超时和跳过计入报告，不更换困难题。

建议同报：获准消息保存率、处理覆盖率与最长积压时间、重复产物率、引用可核对比例、当前态/历史态/原话查询的命中、主张正确率、条件遗漏、助手建议误采纳、撤回/删除后残留、原文回查占用、LLM/embedding 次数与实际 token、存储增长和 p50/p95。安全和身份约束对合成样例要求零违例；性能与成本先录基线再定门槛，不以“马上省一半 token”或“毫秒级永久可用”作为未经测量的承诺。

## 十四、优先级与暂缓项

| 优先级 | 建议 | 理由 |
|---|---|---|
| P0 | 提交后确认保存、消息身份、显式归属、持久任务 | 这是“先存原文”有意义的前提；没有这些，模型不稳或重启仍可能漏原话。 |
| P0 | 来源关联、角色与条件辨别、删除/人工裁决抑制 | 先增加原文量而没有这些，会把旧错话和助手猜测反复提取为事实。 |
| P1 | 长会话分段、版本化重提取、有限原文回查与可见状态 | 让原文成为能持续修复知识、帮助回答的资产，而非另一个看不懂的堆积库。 |
| P1 | 一条真宿主闭环、备份恢复及分阶段质量对照 | 验证实际有用及可恢复，给后续优化提供可信分母。 |
| P2 | 更多宿主、工具原始输出、附件、多模态与更大规模向量优化 | 应由真实缺口驱动，避免第一期把身份、成本、权限与恢复范围一起放大。 |
| 暂缓 | 换主存储、分布式队列、自动全量重提取、自动压缩后删原文 | 当前目标不需要这些；会增加迁移和误写风险，掩盖核心验收。 |

**最终建议：把“记住”的第一步交给可靠的存储，把“理解”交给可复核的提取，把“是否采纳”交给现有治理。** 用户说过的话可以长期留作依据；系统对这些话的解释可以更新、拒绝或撤回。后续能力是否值得做，以真实对话中少漏记、少误记、能纠错、能删除的证据决定。
