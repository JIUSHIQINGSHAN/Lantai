# ADR-0097: 石室封存验真与写锁收紧

**日期**: 2026-11-25  
**状态**: Accepted  
**关联**: [ADR-0074](0074-shishi-core-memory-vault-and-tamper-proofing-engine.md)

石室既有不可变检查只保护自身写入口，普通 `put_core_memory` 可以覆写正文并清除封存元数据；检查之后另一个事务才加锁，也能被旧写覆盖。读取还会为损坏正文重算摘要后返回，未封存行被算作已验证。保持既有表结构和摘要格式，收紧所有既有核心记忆写入口与石室验真读取。

## 决策

- `ShishiVaultBlock` 为冻结的数据快照，防止调用方意外原地改写；数据库写保护仍由服务权限与条件更新承担。
- 仅接受 `sha256=<64 位小写十六进制>:sealed[:immutable]`。封存解析及旧正文验真共用 `validate_existing_seal`，普通用户不得把损坏封存续写成新合法封存；显式管理员可经石室封存入口裁决恢复。
- 验真报告增加 `unsealed_blocks`。无封存的历史行不算篡改，也不计入 `verified_blocks`；只要存在未封存或损坏块，`is_valid` 就为假。空范围报告为有效且总数为零，不意味着存在已验证资产。
- `get_sealed_blocks` 仅返回元数据合法且摘要匹配的块。验真和封存读取刷新 Session 已缓存的实体，避免同一会话漏看其他写入者已提交的变化。
- 两个核心记忆写入口在 SQL 语句内重验归属与不可变标记；已封存行同时比对原正文和元数据，变动则拒绝旧写。普通核心记忆写入保留并更新可变封存摘要，不得抹掉读取后才出现的封存。首次插入唯一键冲突后的更新同样执行检查。
- 未封存行继续遵守既有的末写胜、数据库端版本递增契约，包括普通 `agent_id` 变动；不采用全行快照比较。既有并发用例 F5a/F5b 继续作为兼容性约束。
- 已明确的用户和租户身份都参与访问收窄。租户双方均有值且不同则不可读写；缺租户的历史行兼容规则保留。本次不改 `(block, namespace, user_id)` 唯一约束，也不建立跨租户同名用户的新存储键。
- 核心记忆两个 REST 写入口将权限拒绝映射为 403；明确的 `ShishiConflictError` 映射为 409，供调用方重读重试，不把其他运行异常伪装为并发冲突。

## 安全边界与兼容代价

沿用 `SHA256(UTF8(namespace + ":" + block_key + ":" + content))` 及 `agent_id` 元数据存储，以免让已有封存全部失效。ADR-0074 中的“签名”在现有实现中实际是**无密钥完整性摘要**，不提供数字签名、来源认证或存储加密；既有分隔串编码也不是新的规范化签名格式。版本、归属和锁标记不在摘要覆盖范围内。

本次能发现摘要仍在时的正文变化及可识别的元数据损坏，并阻断正常应用写入口对不可变封存的覆盖。掌握数据库任意写权限者若同时改正文与摘要、删除封存元数据、直接降锁、回滚或删除整行，仍无法据此可靠归因或证明历史。更强保证需独立可信锚点或密钥管理与存量迁移，不能用本轮测试通过替代这些能力。

报告的 `is_valid` 对未封存行由真变假是有意收紧；调用方应结合 `unsealed_blocks` 区分“尚未封存”和“验真不匹配”。管理员重封存保留原数据库行的用户、租户身份。新增字段保留默认值及原构造参数顺序，既有摘要向量与接口成功响应字段不变。
